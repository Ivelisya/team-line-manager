# 运维手册

日常运维一律走 `fleetctl`（人和 AI 共用）。它调中控 API；中控用自己的 SSH 密钥登录机器，所有写操作和每次远程命令都进审计（`fleetctl audit`、网页侧栏「操作记录」）。

## 1. 准备

在中控上（ssh 进去，root）什么都不用准备：fleetctl 和它的全权密钥由部署装好，见 §14。下面是在别的机器上用 fleetctl 的做法。

1. 在网页「设置 → API 密钥」创建密钥，按用途选 scope（见 `docs/API.md`「API 密钥与 scope」）：
   - 只看：`read`
   - AI 日常运维：`read,write,exec`（给 `secrets` 才能取分享链接，按需再加）
   - 密钥设有效天数，不用了就撤销。token 只显示一次。
2. 取得 `fleetctl`：
   - Windows：`cargo build -p fleetctl --release`，得到 `target\release\fleetctl.exe`。
   - Linux x86_64：跑 `lab/install-fleetctl.sh`（在编译主机上编，见 §9 编译主机），从 fleet-dev 的 `/opt/fleet/dist/fleetctl` 取。
3. 写配置并自检：
   ```
   fleetctl login --url http://192.168.31.60:8080 < 密钥文件     # PowerShell：Get-Content 密钥文件 | fleetctl login --url …；或直接运行、按提示粘贴（会回显）；--token 也能用，但会留在 shell 历史与进程列表里
   fleetctl whoami
   ```
   公网地址用明文 `http://` 时会警告（密钥明文传输）。配置也可用环境变量 `FLEET_URL`、`FLEET_TOKEN`；文件位置（unix 上 0600）：Linux/macOS `~/.config/fleetctl/config.toml`，Windows `%APPDATA%\fleetctl\config.toml`。

约定：脚本和 AI 都加 `--json`（一行 JSON：`ls` / `entries` / `incidents` / `policy ls` / `silence` 是与表格同列的精简对象，单台完整视图用 `show`、`policy show`；`billing` 是订阅、流量额度与最近续费记录合成的对象；其余是 API `data` 原样）；错误走 stderr、退出码非 0（没拿到中控响应时 code 为 `unreachable` 或 `timeout`，后者说明操作可能已执行，先查 `jobs` / `audit` 再决定重试；没加 `--yes` 的危险操作被拒是 `confirm_required`；401 / 403 的 message 末尾另有一行下一步；参数写错由 clap 报，退出码 2、stderr 是纯文本用法提示）；会确认的换线 / 搬空 / 退役，不加 `--yes` 时预览（`--json` 也一样）打在 stdout、确认错误在 stderr；人看的输出时间一律是北京时间；`<机器>` 可写 id、显示名（团队1-06）、线路机名、IP，歧义时命令会列出候选。

## 2. 常见任务 → 命令

| 任务 | 命令 |
|---|---|
| 今天有没有问题 | `fleetctl status` |
| 哪些机器不正常 | `fleetctl ls --status down`、`fleetctl ls --status degraded` |
| 某团队全部节点 | `fleetctl ls --team 团队1`（团队名或 id；`--kind`、`--status` 只认固定取值，写错报错） |
| 一台机器详情、为什么不健康 | `fleetctl show 团队1-06`（看「健康原因」） |
| 最近一天的 CPU/内存/磁盘/网速 | `fleetctl series 团队1-06 --range 24h` |
| 入口的流量与探测 | `fleetctl series 团队1-06 --metric traffic` / `--metric probe` |
| 告警列表、确认 | `fleetctl incidents`、`fleetctl ack <id>`；一台机器的告警历史 `fleetctl incidents --all --machine 团队1-06` |
| 维护前开维护窗口（免得告警刷屏），或预约 | `fleetctl silence add 团队1-06 --for 2h --maintenance --comment 换内核`；软路由（客户现场断电、换宽带）`fleetctl silence add --router 团队2-路由A --for 4h --maintenance --comment 换宽带`，探测点 `--probe 香港`；预约加 `--start "2026-10-23 02:00"`（组织时区，默认北京时间）；只静默一条规则 `--rule agent_offline`（要是这类对象的规则，如软路由的 `router_exits_down`）；`fleetctl silence ls`（「类型」列：机器 / 软路由 / 探测点 / 全部），做完 `fleetctl silence rm <id 前缀>`；全部 `--all --yes`（软路由、探测点也一起；API 密钥最长 24 小时，更长的在网页用账号建；建、删都会通知所有渠道） |
| 到期与续费：快到期的机器、看订阅、登记续费、改订阅 | `fleetctl ls --due 7`（7 天内到期、含已过期的在用机器；`fleetctl status` 的「即将到期 / 已过期」按各台的提前提醒天数算，同续费告警）、`fleetctl billing 团队1-06`（订阅与续费记录）；确认已付款后 `fleetctl renew 团队1-06 --yes`（默认同网页：按订阅周期推一个周期（新到期日由中控算，小月按月末）、金额取订阅价格；一次付几期 `--cycles 3`，按面板 `--to 2027-01-15 --amount 39.46 --note …`）；到期日扎堆时看未来待付清单 `fleetctl billing --due 30d --by-provider`（按供应商 × 到期日分组，原币种小计与 USD 合计，控制台链接；网页「团队与套餐 → 待付」同，每组「登记已付…」），批量登记 `fleetctl renew 团队2-07,团队2-08 --ref "#2041"` 或 `fleetctl renew --provider GOMAMI --due 2026-11-20`（不加 `--yes` 只预览每台的原到期 → 新到期与金额；`--yes` 一个事务登记、审计一条；备用团队和自动续费的默认不选，`--include-spare` 带备用）；改订阅 `fleetctl subscription set 团队1-06 --price 45 --yes`（只改给了的字段；`--price none` 改回跟随套餐）。订阅跟随模板：价格、币种、周期、流量上限跟随**套餐**，账单时区、提前提醒、流量重置（自然月 / 账单日）跟随**供应商**，订阅只存到期日、自动续费和单独设置的项——同一套餐一起调价、改额度改套餐（`fleetctl plan set <套餐> --price 45 --yes`，或网页「团队与套餐」），立即对没单独设置的机器生效；上架选了套餐只要填到期日 |
| 费用统一按美元：看汇率、汇率不对或缺币种时手动设置 | `fleetctl settings fx`（各币种的汇率、来源、上次更新时间；在用但没有汇率的会列出来）；手动设置 `fleetctl settings fx CNY --per-usd 7.12 --yes`（或 `--usd 0.1404`），改回自动 `fleetctl settings fx CNY --auto --yes`，立即更新 `fleetctl settings fx --refresh`。月费、合计都按它折成 USD（见 §16） |
| 服务日志 | `fleetctl logs 团队1-06 --unit fleet-agent --lines 300`（unit：fleet-agent / fleet-xray / fleet-singbox（线路机的 AnyTLS） / ssserver） |
| 中控自己的日志 | `fleetctl server-logs --lines 300` |
| 在一台机器上执行命令 | `fleetctl exec 团队1-06 -- systemctl status fleet-agent` |
| 对一个团队的全部节点执行 | `fleetctl exec --team 团队1 -- uptime`（并发 4，汇总退出码） |
| 软路由出口时好时坏：每个出口的测试次数、失败次数、成功率、连续两轮失败几次、延迟中位 / 最大、当前连接 | `fleetctl router exits 团队2-路由A --range 24h`（1h 按每轮测试数；6h / 24h 按 5 分钟一点；7d / 30d 是小时汇总，次数准、看不出连续失败；延迟只算通了的）；当前状态 `fleetctl router show 团队2-路由A` |
| 软路由的配置被谁改了、什么时候改的、改了哪些出口 | `fleetctl router changes 团队2-路由A [--limit 20]`（`--json` 给机器读；每次采集发现配置文件变了记一条：时间、来源——中控作业（替换 / 换线路机 / 改出口指向 / 同步出口，带作业 id）或「路由上改的」（手改、旁路由上的看门服务重新生成）、出口的增删改，凭据只记「变了」；每台留最近 200 条）；`fleetctl router show` 末尾也带最近 5 条。网页：软路由抽屉的「变更」页签。只记录，不提供回滚 |
| 节点被打，软路由的客户临时走备用出口、过几小时切回（不重启 OpenClash、不断连接） | `fleetctl router show 团队2-路由A` 看「策略组」（哪个 select 组选着它）→ `fleetctl router switch 团队2-路由A <组> <备用出口> --for 4h`（到时自动切回；不确定多久就不带 `--for`，之后 `fleetctl router switch 团队2-路由A <组> --back`）。告警 `fleetctl incidents` 末尾的「建议操作」已经算好了切到哪个出口 |
| 软路由出口参数和入口不一致（告警「软路由出口参数不一致」：轮换凭据后没同步） | `fleetctl router sync 团队2-路由A` 看预览，确认后加 `--yes --follow`（改成入口现在的凭据，地址端口不变；会重启 OpenClash，断开经它的连接）；入口已删除 / 停用的同步不了，用 `fleetctl repoint` 换入口；预览里「未自动同步」的是从没对上过入口的出口（路由上有人加的？），确认是自己的再 `--exit` 点名 |
| 登录机器或软路由（在中控上，见 §14） | `fleetctl ssh 团队1-06`（交互式）、`fleetctl ssh 团队1-06 -- 'df -h'`（退出码同远端）、`fleetctl ssh router <名称>` |
| 供应商与套餐（上架前先确认存在，没有就建） | `fleetctl provider ls`、`fleetctl plan ls [--provider ATTVPS] [--all]`；新建 `fleetctl provider add ATTVPS --code ATT [--tz America/Los_Angeles] [--traffic-rule min] [--traffic-reset billing] [--remind-days 7]`、`fleetctl plan add 基础版 --provider ATTVPS --price 299.99 --currency CNY --cycle monthly [--cpu 2 --mem-mb 2048 --disk-gb 40 --bandwidth-mbps 1000 --traffic-gb 2000]`；改 `fleetctl provider set <供应商> … --yes`、`fleetctl plan set <套餐> --price 309.99 --yes`（只改给了的项，`--tz none` / 规格 `none` 清空；改价、改额度、改时区立即对没单独设置的机器生效）；不再上架 `fleetctl plan set <套餐> --archive --yes`；删 `provider rm` / `plan rm --yes`（还有套餐 / 机器用着时中控拒绝）。套餐重名写 `供应商/套餐` |
| 上架 | `fleetctl provision --file batch.json --dry-run`，确认后 `fleetctl provision --file batch.json --yes --follow` |
| 已有 VPS 节点上多了一个 IP，加成一台节点（同机 IP 节点，见 §6） | `fleetctl provision --kind vps --host 团队1-03 --ip 203.0.113.7 --team 团队1 --relay 线路机2 --yes --follow` |
| 看作业进度、失败原因 | `fleetctl jobs --active`、`fleetctl jobs --failed`（默认只取最近 30 个，`--limit` 最大 500，文字版尾注写总数；`--kind upgrade_agent` 等只看一类；系统发起的作业或停在「需要人工处理」的作业失败时，通知渠道会发「作业失败」，写明重试命令）、`fleetctl job <id> --follow`；失败后 `fleetctl retry <id>` |
| 清理作业记录（上架、测试攒下的已结束作业） | `fleetctl jobs-prune [--before 2026-10-25] --yes`：删已成功、已取消的（连同步骤与日志），失败的、进行中的不动，先报数量；网页作业页「清理记录…」。不清也会每小时自动删 90 天前的 |
| 退役（默认进备用，到期满 1 天自动回收） | `fleetctl retire 团队1-06 --reason 换新机 --yes`：先打印预览——去向（→ 备用-03，哪天起自动回收）、一起进备用的同机 IP 节点、还指向它的软路由出口（不会自动改，要换掉先 `replace`）、原团队的改名。机器照常运行（入口、端口、软路由出口都还在），不建作业。撤销 = 移出备用：`fleetctl rename 备用-03 --team 团队1`。进不了备用的（线路机、没有订阅、已过期满 1 天、上架中 / 上架失败、本来就在备用里）报原因，只能立即回收 |
| 立即回收（不等到期） | `fleetctl retire 团队1-06 --now --reason 到期不续 --yes --follow`：退役作业摘入口、停服务（`--no-cleanup` 不登录清理）、撤令牌，完成时移进回收站；宿主机上的同机 IP 节点一并回收（命令先列出来）。之后机器从面板消失，数据约 93 天内由中控自动清除（入口流量还计入线路机统计的等满 93 天），不需要也没有手动「彻底删除」 |
| 回收站（只读） | `fleetctl recycle ls`（`-q 关键词`、`--source legacy`）、`fleetctl recycle show <id\|名字\|IP>`（`--json` 带回收时的快照）。旧面板的退役机器：`fleetctl recycle import --file legacy.json` 先预演（列出会导入、会跳过的：导入过的、IP 或供应商编号对上面板里还没回收的机器），用户确认名单后加 `--yes` |
| 备用团队与到期回收 | 备用团队只有一个（系统管理：不能新建、取消、删除，可以改名：`fleetctl team set "团队2 备用" --name 备用 --yes`）；`fleetctl team ls` 标出它。退役的、替换下来的机器都在这里，`billing` / `show` 有「备用」一行（「已于 10-21 退役（原 团队2-07），11-17 起自动回收」）。备用团队里**在用**、有订阅的机器，账单时区的今天晚于「到期日 + 1 天」（到期日 10-20：10-21 还留着，10-22 0 点起，即机器视图的 `recycle_on`）时，中控每小时的维护自动走「立即回收」那条路（带清理，宿主机连带同机 IP 节点，操作人「系统」），完成时移进回收站。有进行中作业的跳过、下一轮再看；续费顺延了到期日（含自动续费）就不回收；没有订阅的不回收（要清理用 `retire --now`）。提前通知复用续费告警：到期当天「今天到期，备用节点后天自动回收」，过期第 1 天「已过期 1 天，备用节点明天自动回收」，还有软路由出口指向它（或它上面的同机 IP 节点）、或它上面还有在用（不在备用团队）的同机 IP 节点时后面列出来，这样的备用机器不自动回收（`show` / `billing` 写「软路由出口还指着，不自动回收」或「同机 IP 节点 X 还在用，不自动回收」）；真回收时另发一条「自动回收」通知（发给所有启用的渠道，不看级别）。备用期间故障告警照常通知 |
| 替换节点（新节点接替旧节点，软路由跟着换） | 先上架新节点，再 `fleetctl replace 团队2-01 --with 团队2-20` 看预览，确认后加 `--yes --follow`（见 §6「替换节点」）。不要手改路由配置或数据库 |
| 把节点换到另一台线路机 | `fleetctl move 团队1-06 --to 线路机3 --yes --follow`（分享链接会变，见 §6）；几个节点一律用一条：`fleetctl move 团队1-02,团队1-05,团队1-07 --to 线路机3 --yes --follow`（每台软路由只重启一次） |
| 线路机退役前搬空 | `fleetctl evacuate 线路机2 --to 线路机3 --yes --follow` |
| 节点卡、丢包，要找供应商（要 ping / mtr 原始数据） | `fleetctl diag 团队1-01`（要 exec 权限，每台记审计；只读，不用 `--yes`）：在每台在用线路机上 ping / mtr 节点、它所挂的线路机另测 TCP 握手连 SS 端口（节点 nft 只放行自己的线路机，别的线路机连不上是正常的，不测），在节点上 ping / mtr / 握手到每台在用线路机与对照 1.1.1.1；每段原样输出（源 → 目的、UTC 时间、命令行），最后「判断」一段写入站过滤 / 入方向链路 / 双向 / 出方向。`--out diag.txt` 另存文件直接发给供应商；`--quick` 少测（20 个包、20 次握手，半分钟）；`--count 300 --tcp 200 --interval 0.5` 测久一点。机器上没有 mtr 的只给 ping（上架基线会装 mtr-tiny，老机器 `--install-mtr --yes` 现装一次）；家宽代理没有 SSH，只测线路机 → 它；同机 IP 节点在宿主机上跑、绑它自己的地址 |
| 告警「持续握手丢包」（`tcp_loss_high`） | 先 `fleetctl diag <节点>` 拿原始数据；判断是入站过滤（入站握手丢、出站与 ICMP 正常）就把输出发给供应商，客户受影响时开穿透绕开入站 `fleetctl entry reverse <入口> --on`（见下一行），或换备用 `fleetctl replace <节点> --with <备用>`；摘要带「同供应商 X 共 N 台同时」时先找供应商，不要逐台换。见 §3 |
| 节点放在哪台线路机最好 / 节点连线路机老断 / 换线前 | `fleetctl placement [--team 团队2] [--node 团队2-04]`：各节点到每台线路机近 24 小时的往返中位数与成功率（`*` 当前，`→` 建议换到），近 7 天 TCP 不通告警次数，末尾每台目标线路机一条批量 `fleetctl move A,B --to X`（只是建议，照它执行时先看预览）。网页：「线路」页顶部「节点放置」，建议条上「换 N 个节点…」打开批量换线。不要再到线路机上手写 ping / mtr 脚本逐个测（见 §18 放置矩阵） |

```json

```

`ss_port` 只给 NAT 机填：供应商给的公网端口（节点上 ssserver 固定监听 8388），非 NAT 机省略。供应商把公网端口映射到机器 8388 的，直接填那个端口；
供应商是同号映射（公网 P → 机器 P）的也填 P，收敛时节点的 nft 表 `ss_guard` 会多一条 nat 链把 P 转到 8388，入站过滤照常只放行线路机。

端口转发型 NAT 节点（供应商给一个公网入口 IP 加几个同号映射端口，机器出站的公网 IP 和入口 IP 不同，来源 IP 保留）：`--ip` 填入口 IP，`--ssh-port` 填映射到 22 的公网端口，
`--ss-port` 填映射给 SS 的公网端口，`--egress-ip` 填机器出站的公网 IP，例如 `fleetctl provision --kind vps --ip 125.103.212.100 --ssh-port 16350 --ss-port 16351 --egress-ip 133.106.194.112 …`
（批量文件条目写 `"egress_ip"`）。线路机连入口 IP:ss_port，出口验收 / 出口探测期望看到出口 IP；之后改或清用 `fleetctl rename <机器> --egress-ip <IP|none>`（none = 出口跟随 IP）。

同机 IP 节点在条目里写 `"host": "团队1-03"`（宿主机的名字），不写 `ssh_port`、`login`、`ss_port`、`provider`、`plan`。

root 密码不要写进文件：条目里省略 `login` 则用中控的密钥；首次登录必须用密码时，单台上架用 `--ssh-password-env VAR`。

`--dry-run`（网页的「检查」）在 SSH 端口通了之后会用中控密钥试登录一次（只读 `/etc/os-release`，不记主机指纹）：
- 报「中控密钥登录不了 ip:22（密钥被拒），也没填 root 密码」：机器上还没有中控公钥。二选一——把报错末尾的公钥（就是中控的 `/etc/fleet/ssh/id_ed25519.pub`，网页上架页「root 密码」下有「复制中控公钥」）录进供应商面板的 SSH 密钥（多数面板要重装系统才生效）或机器 root 的 `~/.ssh/authorized_keys`；或者给 root 密码（`--ssh-password-env VAR`），作业会用它装上公钥、之后丢弃。供应商面板里「已经录过密钥」却仍报这条，多半录的不是中控这把。
- 「提醒：系统是 Ubuntu 20.04，已过标准支持期…」：不拦上架（作业日志里也会记一条 warn），建议找机会重装成新版本。过期表在 `jobs/scripts.rs` 的 `OS_EOL`（现在是 Ubuntu < 22.04、Debian < 12），版本过期了改那里。
- 端口不通（「SSH ip:22 连不上（3 秒没有响应）」）时不会试登录：机器还没装好系统或防火墙没放行。

## 3. 故障排查流程

按这个顺序，前一步解释不了再进下一步：

1. **看全局**：`fleetctl status`（告警表格最多列 20 条，严重的在前、同级新的在前，多的写「另有 N 条」，全部用 `fleetctl incidents`；`--json` 不截断）。告警里的「规则」决定走向：
   - `agent_offline`：到 2。
   - `no_entry`：节点没有入口；`fleetctl entries <机器>` 确认，缺就 `POST /machines/{id}/entries`（网页「新增入口」）。
   - `egress_fail` / `tcp_fail`：入口到出口不通，到 3。作业「出口验收」一直报「超时 12 秒」、或报「线路机 X 连不上节点 SS 端口」时先查节点的主机防火墙：供应商镜像自带的 ufw / firewalld 常只放行旧线路机（实际发生过：换线路机后验收卡了 7 分钟，节点上 ufw 的 8388 只放行旧线路机）。收敛脚本（上架、`ss_refresh`、换线路机的防火墙步骤）会在 ufw / firewalld 运行时给放行名单里的线路机 IP 加 SS 端口的放行规则（ufw 规则注释 `fleet-ss`，名单里已没有的旧线路机规则同时删掉；不关用户的防火墙，不重启 ssserver），作业日志写「主机防火墙：…」；规则没改成、或只有 iptables 且 INPUT 默认丢弃时日志里有 warn，需要到节点上手动放行线路机 IP；云厂商安全组中控管不到，只能到供应商面板放行 SS 端口（tcp、udp）。
   - `tcp_loss_high`（持续握手丢包，警告，节点算降级）：近 30 分钟线路机 → 节点的入口 TCP 探测（每条入口每 30 秒一次）失败 ≥ 5% 且至少 3 次，或成功建连里带 SYN 重传的 ≥ 15% 且至少 5 次（样本至少 30 次）；两个比例都低于一半（2.5% / 7.5%）连续 10 分钟才恢复。和 `tcp_fail` 互补：那条看连续失败（真断了），这条看零散但持续的失败——供应商只丢一部分入站新建连接时（2026-10-27 DeerVPS 4 台从 09:30 起 10–20% 超时、22–40% 重传，`tcp_fail` 只零星开过、健康一直正常）就是这样。摘要写次数与比例，同一时刻同供应商（或同 /24）的其他在用节点也在触发时追加「同供应商 X 共 N 台同时（可能是供应商入站丢包）」：这时是供应商的问题，按下面第 7 步处理，不要逐台查。经离线、维护中、Xray 停了的线路机的入口不算；穿透入口没有这项探测、不算，节点的入口都切成穿透后告警自动恢复；闲置备用只降级、不告警。
   - `relay_apply_lag` / `relay_apply_error`：线路机没应用最新配置，到 4。
   - `relay_xray_down`：线路机上的 xray 停了，到 4。
   - `relay_unreachable`：探测顺序里此刻在用的那一路（第一个能用的探测点，都用不了时中控代测，见 §17）连续 3 轮（每 30 秒一轮，轮流连线路机的各个入口端口）连不上线路机的客户入口（public_host + 端口），或同一个端口最近 3 次都连不上，健康状态就变故障；告警再持续 60 秒才开——整台不通从第一次失败算起约 5 轮、2.5 分钟，单个端口坏了是它连续 3 次之后再 1 分钟。摘要开头写是谁测的（「香港探测点连续 3 次以上…」「香港探测点（代替离线的PVE探测点）连续 3 次以上…」「中控（代替离线的香港探测点）…」），括号里是失败的端口与原因；连上一次原因就消失，再满 60 秒恢复。只是 TCP 建连，不做 REALITY 握手。线路机 agent 也离线多半是机器挂了；agent 在线则查线路机防火墙、供应商是否封了端口（`fleetctl exec <线路机> -- 'ss -ltnp'` 看端口在不在听）。只有探测点连不上、中控连得上（`fleetctl probe ls` 看到各路的延迟与成功次数）多半是大陆方向的线路或封锁问题，中控看不到也不代表客户没事。摘要后面带「；所有线路机同时连不上，可能是供应商整体故障」时，测的这一方对照目标是通的、三台以上线路机却一起连不上：先看供应商（同一家、同一个网段的几台一起出问题），而不是逐台查。
   - `probe_point_offline`：探测点超过 3 分钟没上报，或在线但 3 分钟里的检查都作废了（它自己连不上对照目标，摘要写「在线，但最近 N 分钟的探测都无效：…」）（警告），见 §17。
   - `clock_skew`：agent 所在机器的时钟偏了超过 1 分钟（读数会缺失或停在旧值）；`fleetctl exec <机器> -- 'timedatectl'` 看 NTP 是否同步，没开就 `timedatectl set-ntp true`（修改状态，先确认）。
   - `renewal_due`：续费提醒，不是故障（不改健康状态）。到期前是警告，过期后同一条告警升为严重（旧的 `renewal_overdue` 并进来了）。开了自动续费的到期后由中控按周期顺延、自动记续费（只记账，供应商那边要自己设好扣费）。网页告警页这一行可直接「登记续费」（或 `fleetctl billing <机器>` 看订阅、确认已付款后 `fleetctl renew <机器> --yes`），下一轮评估（≤30 秒）自动恢复。
   - `traffic_quota_high`：流量额度吃紧（本周期已用 ≥ 90% 警告，≥ 100% 严重：供应商可能限速或另收费），不是故障、不改健康状态。`fleetctl billing <机器>` 看本周期已用与上限（注明跟随套餐还是单独设置）；找供应商加流量、调高上限（整个套餐都加了改套餐，只这台加了 `subscription set --traffic-gb`）或把流量分走。新周期开始、上限调高后下一轮评估自动恢复。没到 90% 但按近 7 天日均预计 7 天内（重置前）用满时也开警告，摘要写预计日期（`fleetctl billing` / `show` 有「预计用满」一行，网页卡片与费用页同一句；已在告警的要预计晚于 7 天 + 12 小时才恢复）；要搬走入口用 `fleetctl rebalance <线路机>` 看建议。
     流量周期按供应商的「流量重置」：自然月 = 账单时区每月 1 号起，账单日 = 每台机器到期日是几号就几号起（如 GOMAMI；月份没有这一天按月末），滚动 30 天 = 账单时区的今天往前 29 天起、没有重置日（如 Blossom，告警写「近 30 天流量已用」）；单台不同的用 `--reset-day` 单独设置（设了就按月）。
     已用按 agent 选中的网卡计量（`show` / `billing` 写「按 ens3 计」：默认路由所在网卡 ∪ 配有公网地址的物理网卡；特殊机型在 agent.toml 写 `nic_ifaces = ["ens3"]` 指定），规则跟供应商（目录 → 供应商的「流量计量」：双向是下行 + 上行；单向只记其中一个：取较小 / 取较大 / 只算上行 / 只算下行，GOMAMI 是取较小；不知道的默认取较大），某台机器的计费方式和供应商不同时在它的费用页签（或 `fleetctl subscription set <机器> --traffic-rule sum|max|min|out|in|none`）单独设置；家宽代理和同机 IP 节点没有网卡读数，按业务流量、下载加上传（不跟供应商的计量规则；网页额度悬停、`billing` 都写「按业务流量，下载加上传」）。上限是十进制 GB（同供应商面板）。
     不再按面板校准（`--used` 已删，接口 400）：agent 的网卡累计值跨重启、开机接续，离线期间的量恢复后记进恢复的那一小时，周期从头到尾都有 agent 数据时就是完整的。周期中途上架的，`billing` 写「X 起统计，之前的用量不在内」（实际剩余可能更少），下个周期自动完整。割接时录的两条接入前读数（线路机1 / 2）只读保留，`billing` 写「接入后实测 A，加上接入前的面板读数 B（Y 重置后只算实测）」（已用 = A + B；总览的本月业务流量只有接入后的，中途接入的标「（10-22 起）」），到各自下次重置后自动失效。
   - `nonbusiness_traffic_high`（非业务流量偏高，警告）：VPS 节点连续 2 个完整小时网卡合计超过业务流量的 4 倍、多出的超过 2 GB（正常约 2.4 倍）——有不经过入口的流量：被扫描、被灌包、机器被拿去干别的（挖矿、发包、跑代理）。这部分照样算进供应商额度。`fleetctl logs <节点>` 看有没有异常登录与服务；`fleetctl exec <节点> -- 'ss -s; nft list ruleset | head -50'` 看连接数与防火墙，再 `exec <节点> -- 'ss -tnp | sort -k5 | head -50'` 看连着谁、是哪个进程。确认是被滥用的转告用户（改密码、重装、封端口都是修改，先确认）；连续 2 个小时回到正常自动恢复。
   - `business_traffic_spike`（业务流量突增，警告）：节点最近一个完整小时的业务流量超过近 7 天同一小时中位数的 5 倍且超过 5 GB（数据不满 3 天不判）。多半是有客户在大量下载，也可能是入口分享出去被滥用。`fleetctl traffic --node <节点> --days 7` 看每天的量，`fleetctl access sources --node <节点> --window 24h` 看是哪些来源、`access targets --node <节点> --window 24h` 看在访问什么；需要先保住别的客户时按告警的「临时切到…」把用着它的 select 组切到别的出口（4 小时后自动切回）。连续 2 个小时回到中位数的 2 倍以下（或不到 5 GB）自动恢复。被打（灌包、DDoS）时 agent 常断线、网卡读数上不去，这两条抓不到，那时报的是出口不通（`egress_fail`）。
     和供应商面板对不上时：先看 `fleetctl show <机器>` 的计量网卡是不是供应商计费的那块（漏了附加公网 IP 的网卡、算进了内网网卡）、agent 是不是新版本（旧 agent 重启会丢十几秒）；再看周期口径——供应商按开通时刻而不是 0 点重置、按滚动 30 天、按入加出合计，都会差出一截，改供应商的「流量重置」「流量计量」而不是手填数字。
   - 告警恢复后 30 分钟内又出现会重开原告警（`reopen_count` +1，告警页显示「反复 N 次」），不会每抖一次发一对触发/恢复通知（报过恢复后 5 分钟内复发的先不报，满 5 分钟仍在才报）。机器、软路由、探测点、中控的告警都是这样；悄悄关掉的（对象删了、停用了）不重开。隔得更久的复发是新告警，但近 7 天同对象同规则开过 ≥3 次时告警页标「近 7 天第 N 次」，`fleetctl status` 末尾「近 7 天反复」列出这些对象；近 24 小时第 2 次起，触发通知摘要末尾带「（近 24 小时第 N 次）」。这是换线或替换的信号，不要只确认。严重度升级（如警告升严重）时马上再发一次「触发」，并清掉之前的确认。
   - 去抖：原因连续出现满 60 秒才开告警、连续消失满 60 秒才恢复（量到的时长留 5 秒余量）；探测类开得更慢（`egress_fail` 150 秒、`tcp_fail` 90 秒），偶发一次探测失败不报。折成次数：出口探测每 60 秒一次，约连续 3 次失败才开；TCP 每 30 秒一次，约 4 次；`relay_unreachable` 的原因本身就要连续 3 次，再叠 60 秒（见上）。探测类恢复按次数：当初失败的入口连续 2 次探测成功就恢复——agent 在结果翻转后约 10 秒补探一次、马上上报，出口探测失败期间改 30 秒一次，出口恢复后约半分钟告警就恢复（旧 agent 没有补探，约 1–2 分钟）。续费类、流量额度不去抖。
   - 评估时机：告警每 30 秒评估一轮；上报里探测结果翻转（含失败转成功后还在确认恢复的；连续失败不唤醒，留给那一轮）、agent 从离线回来、Xray 起停，线路机连通性结论变了，静默 / 维护变了，都马上评估一次（两次至少隔 2 秒），不等那一轮。
   - 软路由：离线连上就恢复（中控看着本机的隧道端口，隧道一连上马上采一次），连不上满 3 分钟（同出口不通的 180 秒）才开 `router_offline`；出口「连续两次延迟测试不通」不另外去抖，不通的出口每轮采集（30 秒）单独重测，连续两次测通就恢复（约 1 分钟）。见 §19。
   - `central_channel_failing` / `central_backup_stale` / `central_disk_low` / `central_ingress` / `central_view_stuck` / `central_tunnel_host`：告警对象是「中控」自己（通知渠道发不出去、备份停了、磁盘快满、大批 agent 同时连不上中控、机器视图算不出来、软路由隧道回连的主机不是中控），见 §12。
   - 维护中的机器：进行中的告警保持原状，不算恢复；维护结束后按那时的状态再判。线路机维护时，经它探测的节点出口 / TCP 结果同样判不出（不开、开着的不恢复）。
     软路由、探测点也可以单独开维护窗口（`silence add --router` / `--probe`，网页软路由抽屉「管理 → 维护窗口」、设置 → 探测点那一行的扳手）：开着的告警保持原状（不恢复、不发通知），不开新的，到期后按那时的状态再判；卡片 / 列表显示「维护」。只静默一条规则（不标维护）时只挡这一条，同机器。全部的维护窗口对它们同样算维护中。
   - 判不出的不算恢复，告警保持原状：线路机 agent 离线或维护中时节点的出口 / TCP；agent 离线时 CPU / 内存 / 磁盘持续偏高与时钟偏差（负载类回来后还要攒够 5 分钟样本）；中控停机超过 5 分钟重启后、新的检查不足 3 轮时的「客户入口连不上」；主来源的探测点离线、暂由中控代替（或标灰）期间的「客户入口连不上」（中控连得上不算恢复，等探测点回来再判）。
   - 通知先写进库里的发送队列（`notify_outbox`）再发：中控重启、部署后接着发，不丢。每个渠道一个发送任务，同一渠道内按入队顺序逐条发（一批告警同时触发时不会并发打到同一渠道），渠道之间互不等待（一个渠道一直超时不拖慢别的）。发送失败（网络错误、5xx）隔 0.5 秒、2 秒、10 秒、30 秒、1 分钟、之后每 2 分钟重发同一条（后面的排着），回 429 时按渠道给的等待时长（Telegram 的 `parameters.retry_after`、通用的 `Retry-After` 头，最多 60 秒）；渠道拒绝（令牌不对、飞书回的 `code` 非 0）不重试，记一条失败。入队满 30 分钟还没发出的放弃，发送记录里记一条失败；渠道连续失败满 5 分钟另开告警 `central_channel_failing`。某个渠道没收到一条告警的「触发」（放弃了，或渠道是后来加的），这条告警恢复时也不给它发「恢复」。
   - 合并发送：机器、软路由同一规则的几台在 60 秒内先后触发（或恢复），每个渠道合成一条消息——标题「【严重】告警触发：3 台 出口不通」，逐台列出名字与摘要（超过 10 台列前 10 台、写「另 N 台」）。为此这两类的触发 / 恢复入队后先等一等：最近一条同类入队后 20 秒没有新的，或首条入队满 60 秒，就发，严重的也最多因此晚 60 秒。不合并的（中控自身、探测点、来源画像的告警，持续提醒、静默变更）不等，也不被等着的批挡住，排进来就发。不同规则、触发与恢复、持续提醒不合并；中控自身、探测点、来源画像的告警照旧一条一条发。发送记录仍每条告警各记一条。
   - 新建、删除静默 / 维护窗口会给所有启用的渠道发一条「静默 / 维护变更」（谁、新建还是删除、对象、维护还是静默、起止、备注；不看渠道的最低级别，也不受任何静默影响）：全部机器的一律发（含预约的），单个对象（机器、软路由、探测点；对象写成「软路由「团队2-路由A」」这样带类型）的只在此刻生效时发。
2. **agent 离线**：`fleetctl show <机器>` 看最近上报时间；`fleetctl exec <机器> -- 'systemctl is-active fleet-agent; uptime'`。exec 返回 255 且 stderr 是连接失败 → 机器本身不通（去供应商面板看机器状态/重启）。agent 没运行则 `fleetctl logs <机器> --unit fleet-agent` 找原因，再 `fleetctl exec <机器> -- systemctl restart fleet-agent`（修改状态，先确认）。
   中控或库停过之后：停机这段不算 agent 的沉默（停之前在报的，恢复后它退避中的重发最长约 45 秒才到，这期间不判离线、不开告警，等摘除的作业也不判线路机不在线）；停之前就不报了的照样离线。
3. **入口不通**：`fleetctl show <节点>` 看入口的 TCP/出口探测；`fleetctl logs <节点> --unit ssserver`；`fleetctl exec <节点> -- 'ss -ltnp | grep -E "8388|ssserver"'`；再看线路机 `fleetctl logs <线路机> --unit fleet-xray`。告警对象是线路机时，是它的直出入口（没有节点、没有 TCP 探测）出口不通：看线路机自己的出网（`fleetctl exec <线路机> -- 'curl -sS -m 10 https://1.1.1.1 -o /dev/null -w %{http_code}'`）和 fleet-xray 日志。
   同机 IP 节点（`show` 里有「宿主机」）：`logs <节点> --unit ssserver` 看的是宿主机上它自己的实例 `fleet-ssserver@<SS 端口>`，`exec <节点>` 在宿主机上执行；它的 agent 离线、高负载告警都在宿主机名下。出口不对时 `fleetctl exec <节点> -- 'ip -4 addr; curl -4 -sS --interface <它的 IP> <中控地址>/echo'` 看 IP 还在不在网卡上、回显的是不是它自己。
4. **线路机配置未应用**：`fleetctl show <线路机>`（代数与 apply_error）；`fleetctl logs <线路机> --unit fleet-agent`；`fleetctl logs <线路机> --unit fleet-xray`。xray 配置错误会写在这里。
5. **作业失败**：`fleetctl job <id>` 看失败步骤和日志；修好原因后 `fleetctl retry <id>`；放弃用 `fleetctl cancel <id>`（已完成的步骤会补偿回退）。报「主机指纹变化」且确认机器重装过：`fleetctl retry <id> --reset-host-key`；报「没有可用的 root 密码」：`ROOT_PW=… fleetctl retry <id> --password-env ROOT_PW`（网页作业的「重试」里同样能勾选 / 填写），或把报错末尾的中控公钥录进供应商面板 / 机器 root 的 `authorized_keys` 后直接 `fleetctl retry <id>`。
   作业日志里的「引擎错误：…（10 秒后从这一步重做）」多半是库暂时连不上（PG 重启）：作业不失败，库恢复后自己从这一步接着做，不用重试；「中控正在重启：「…」等重启后接着做」是部署时停在了两步之间，重启后自动接着做。
6. **中控本身异常**：告警对象是「中控」的按 §12 处理；`fleetctl server-logs` 看日志，读不到时按错误提示授权 journal（`usermod -aG systemd-journal fleet` 后重启 fleet-server）。中控整个挂了时 fleetctl 也用不了，靠死人开关（§12）知道，ssh 进中控按 §4 处理。
7. **节点时好时坏、新建连接偶尔失败（`tcp_loss_high`、卡片心跳条零散的红块 / 黄块）**：`fleetctl diag <节点> --out diag.txt`。看最后的「判断」：
   - 入站握手丢（超时、首次握手被丢 = SYN 重传）、出站握手与双向 ICMP 都正常 → **入站过滤**：供应商只丢进来的新建连接（已建连接、出站不受影响，所以出口探测、ping 都正常）。把 diag.txt 发给供应商（里面就是他们要的 ping / mtr 原始数据，带 UTC 时间）；客户受影响时开穿透绕开入站（`fleetctl entry reverse <入口> --on`，§6「穿透入口」），或换到备用节点（`fleetctl replace <节点> --with <备用>`）；同供应商多台同时的，换也优先换别家。
   - 入方向 ICMP 也丢、出方向正常 → 供应商入方向的链路问题：mtr（线路机 → 节点）从哪一跳开始丢就是哪一段，发给供应商。
   - 双向都丢 → 机房 / 网卡（或节点本机）的问题；只在某一台线路机 → 节点丢 → 那一段路由，`fleetctl placement --node <节点>` 看换哪台线路机。
   - 没测到 → 多半是间歇的：在告警开着、卡片出现红块时再跑一次，或加大次数（`--count 300 --tcp 200`）。

## 4. 何时才需要直接 ssh

默认不需要。只有这些情形：

- 中控本机故障（fleet-server 起不来、数据库挂了）：fleetctl 依赖中控，此时 ssh 进中控机用 `journalctl -u fleet-server`、`systemctl`、`psql` 处理。
- 机器的 SSH 指纹变了或 known_hosts 校验失败（exec 返回 255，stderr 提示主机密钥）：先确认不是 IP 冲突或被冒用（比如服务商确实重装了系统），再对这台机器 `fleetctl upgrade-agent`：它会因指纹不符失败，`fleetctl retry <作业> --reset-host-key` 重新记录指纹（只有指纹不符失败的作业能这样重试；同机 IP 节点对宿主机做）。
- 要交互式操作（编辑文件、长时间抓包）或持续数分钟的任务，超出 exec 的 10 分钟上限与 256 KiB 输出上限（在网页上先用网页终端，§15；它不够用时，如传文件、一次要开 2 小时以上，再按下面的办法）。
- 给机器装中控没管理的东西。

后两种在中控上用 `fleetctl ssh <机器>`（软路由 `fleetctl ssh router <名称>`，§14）：用中控的密钥、只认中控记下的主机指纹，登录记审计。ssh 会话里做的事只记了登录、不记命令：做了改动事后在备注（`fleetctl rename <机器> --note …`）里记一笔。

## 5. 安全要点

- 密钥按最小 scope 发；`exec` 等于 root shell，只给确实需要的 AI 或人。
- exec 的命令全文会写进审计，不要在命令里放密码、令牌。
- 网页终端同样是 root shell：只给登录用户（API 密钥不行），每次打开前再输一次密码（开了两步验证是验证码，同一会话 5 分钟内免输）；终端里输入的命令**不进审计**，只记谁、哪台、多久、多少字节、为什么断（§15）。要留痕的改动用 `fleetctl exec`。
- 登录有限速（15 分钟窗口，来源 = IPv4 地址或 IPv6 /64）：同一用户名从同一来源错 5 次、同一来源错 20 次、同一用户名不分来源错 100 次会被 429 拒绝；最后这条不拦你 30 天内登录成功过的来源（攻击者换很多地址凑满 100 次也锁不住你常用的网络）。别人在别处输错不会把你锁在外面；`fleet-server user-set` 重设密码时清掉该用户的失败记录、全部会话与登录成功过的来源。两步验证码输错另有上限：同一用户名 1 小时 10 次，不分来源（知道密码的人换地址猜码也只能猜这么多；被封时你自己也要等，见到这种情况就该改密码）。
- **开两步验证**（网页「设置 → 账户安全」）：这个账户能以 root 登录全部机器，密码之外再要手机认证器上的 6 位验证码。开启时会给 10 个恢复码，只显示一次：存进密码管理器或打印出来，和手机分开放；每个只能用一次（登录页的验证码框里直接输），快用完时在同一页重新生成一组（旧的全部作废）。改密码、看 / 撤销登录会话（不认识的设备立即撤销、「退出其它设备」）也在这一页；改密码后其它设备自动退出。开启两步验证、退出其它设备、新建 API 密钥都要再输一次密码（开了两步验证还要验证码）：只偷到浏览器会话的人做不了这些。API 密钥不随改密码失效：怀疑会话或密码泄露时，改密码时勾上「同时撤销所有 API 密钥」，再按需新建。
- 手机和恢复码都丢了：在中控上以 root 执行 `fleet-server totp-reset -c /etc/fleet/fleet.toml <用户名>` 停用该用户的两步验证（恢复码一并作废，写审计 `auth.totp_disabled`，不输出任何秘密），然后用密码登录、立刻重新开启。忘了密码用 `fleet-server user-set`。
- 删除或停用账号：在中控上以 root 执行 `fleet-server user-del -c /etc/fleet/fleet.toml <用户名>` 删除（`--disable` 只停用，之后 `user-set` 重设密码即恢复）；该账号的登录会话马上作废，写审计 `auth.user_removed` / `auth.user_disabled`（操作者 cli）；不能删或停用最后一个能登录的账号。API 密钥不属于账号，不受影响。
- API 密钥（fleetctl、脚本）不经过两步验证，也不能调 `/account/*`：密钥本身就是凭据，按最小 scope 发、设有效期。
- 有 `write` 权限就能上架线路机、把节点挂过去，那台线路机的 agent 会收到节点的 SS 密码与代理账号：`write` 实际上也能拿到凭据，按凭据级别发。
- 通知渠道只有 Telegram 和飞书两种。飞书的 Webhook 地址只许 `open.feishu.cn`、`open.larksuite.com` 两个主机（https），别的一律拒绝；Telegram 的 `api_base` 不能指向内网、环回、链路本地（云元数据）地址，也不能是内嵌 IPv4 的转换地址（NAT64 `64:ff9b::/32`、6to4 `2002::/16`、Teredo `2001::/32`），域名在发送时只解析公网地址；发送不走环境变量里的 HTTP 代理（代理会替它解析域名）。这套检查没有开关（`fleet.toml` 里不再有 `[notify] allow_private`，写了也忽略），只有测试能放开。改 Telegram 的 `api_base` 要同时重新填 `bot_token`。
- 全部机器的静默 / 维护等于把监控关掉：API 密钥建的最长 24 小时（账号登录的 30 天）；新建、删除静默 / 维护都会通知所有启用的渠道（不受静默影响），悄悄关监控会被看到。
- 中控：fleet-server 在 systemd 沙箱里运行（无任何特权、只写 `/var/lib/fleet`、系统调用白名单），`/etc/fleet` 归 root、fleet 只读；部署后 `journalctl -u fleet-server` 里出现 SIGSYS / Permission denied 先看沙箱。Caddy 管理接口在 `/run/caddy/admin.sock`（只有 caddy 能连），改配置后用 `systemctl reload caddy`，直接 `caddy reload` 不带 `--config` 会连不上。网页带 CSP（只许本站脚本），不能再加内联脚本或外部 CDN。
- 线路机：Xray 以 systemd 动态用户运行（不是 root），配置由 systemd 经标准输入交给它，读不到 `/etc/fleet-agent`、`/etc/ssh`，连不上本机的 systemd / D-Bus；访问日志实际在 `/var/log/private/fleet-xray`（`/var/log/fleet-xray` 是符号链接），agent 靠 `CAP_DAC_READ_SEARCH` 读。Xray 与 VPS 节点的 ssserver 都拦了链路本地网段与 100.100.100.200（客户经域名也到不了云元数据服务）；机器的 `/etc/resolv.conf` 用链路本地地址的 DNS（169.254.x、fe80::，GCE、Oracle 等不经 systemd-resolved 的镜像）时拦了就解析不了域名，这样的机器上拦截照旧，改用公共解析器（见下一条），作业日志记一条 warn。这些单元改动在升级 agent / 收敛时写入，Xray 下次重启、ssserver 下次收敛时生效。agent 上报按机器限速（突发 600 份、每秒补 1 份，超了回 429），agent 拒绝连公网的明文 http 中控。
- 节点出站黑名单：节点收敛步骤（上架新节点，替换节点的新机器同样走它）里写 `/etc/shadowsocks-rust/fleet.acl`（shadowsocks-rust 的 `[outbound_block_list]`），配置里 `"acl"` 指向它。目标是回环、私网（10/8、172.16/12、192.168/16）、链路本地、CGNAT、IPv6 回环 / ULA / 链路本地、IPv4 映射地址（::ffff:0:0/96）的连接被拒，域名按解析出的 IP 判，所以客户把域名解析到 127.0.0.1 / 10.x 也碰不到节点本机服务和供应商内网；挡的是目标不是源，同机 IP 节点的 `outbound_bind_addr`（含 NAT 的 10.116.x）照常出站。已在线的存量节点用 `fleetctl ss-refresh` 带上（见上面「重新下发 SS 配置」一行）；带上那次 ssserver 重启一次（断开已有连接几秒）。
- 线路机 DNS 是链路本地地址时：装 Xray 单元时（上架、升级 agent）写 `/etc/fleet-xray/resolv.conf`（1.1.1.1、8.8.8.8、2606:4700:4700::1111），单元用 `BindReadOnlyPaths=-/etc/fleet-xray/resolv.conf:/etc/resolv.conf` 把它挂到 Xray 看到的 `/etc/resolv.conf` 上：REALITY 伪装目标、写成域名的家宽代理上游与节点地址、直出都经公共解析器解析，Xray 的配置不变。不是链路本地 DNS 的机器上没有这个文件，Xray 用系统的。上架时装单元不重启 Xray（agent 随后才拉起它）；装 agent（上架、升级）时先装 Xray 单元、后换 agent，正在跑的 Xray 看到的还不是这份文件（单元刚换上挂载）就重启一次 Xray（会断开这台线路机上客户的连接，作业日志记一条说明），重启过的不再重启。同一台机器同时只处理一份上报、一份应用回报，另一份回 429（Retry-After 1 秒）；agent 本来就逐份发送，正常碰不到。
- 危险操作（退役、删除、轮换、批量升级、会改状态的 exec）先向负责人确认，再加 `--yes`。

## 6. 换线路机 / 搬空线路机 / 替换节点 / 退役与回收站 / 穿透入口 / 同机 IP 节点

### 替换节点（新节点接替旧节点，软路由跟着换）
用于把一台节点换成新买的机器、客户那边不用动：团队软路由上指向旧节点的出口（如「节点01」）改成新节点的入口，新节点接旧节点的编号，旧节点进备用团队。
1. 先把新节点上架到同一团队（拿到临时编号，如 团队2-20，入口生效）；别的团队的在用节点也行，替换时改到旧节点的团队。
2. `fleetctl replace 团队2-01 --with 团队2-20`：只打印预览——新节点 团队2-20 → 团队2-01、旧节点 团队2-01 → 备用团队的空号、要改的路由与出口（现在的 server:port → 新的）、新节点原团队的编号压缩、阻断原因。旧节点默认去备用团队（只有一个），要放别处用 `--to <团队>` 指定，`--number` 指定编号；`--no-routers` 只交换编号。网页：节点抽屉「管理」→「替换为…」，或卡片菜单。
3. 确认后加 `--yes --follow`。作业两步：
   - **改软路由出口**：预览按各路由最近一次采集列出；执行时按路由当时的配置再定一次（发起之后新加的指向旧节点的出口照改，已经不指向的不改，和预览不一样时作业日志写明），出口对上的入口属于旧节点的都改（同团队有两台配置相同的路由就两台都改）。同一台路由一次只有一个作业在改，别的作业在改就在这一步排队（不算超时，排队时能取消）。新入口按线路机一一对应（旧入口在哪台线路机就换成新节点在同一台上的入口；对不上时新节点只有一个在用入口就用它，否则预览里报错说明）。有一台路由不在线：一台都不改，作业失败，路由恢复后重试。在线的路由 OpenClash 配置读不了（读失败、解析不了）时，哪怕快照里看不出它有出口指向旧节点，也一台都不改、作业失败（以前是跳过这台，旧节点到期回收后客户的出口就断了）：修好配置后重试，确认那台路由没用这个节点才重新发起加 `--no-routers`（别的作业正拿着这台路由的锁时读失败不算：多半是对方在重启 OpenClash 掐断了隧道，这里排队等它改完再读）；预览对任何团队的配置读不了的路由都提醒。路由上根本没有源配置（OpenClash 没配）的算没有出口。改回时按路由现在的隧道端口连（卡住期间重新接入换过端口也连得上）；还有作业改过它、没确认改回时删不了这台路由（409，给出作业 id）。在线的一台一台改：经隧道在路由上备份 OpenClash 的源配置（`uci get openclash.config.config_path`）到 `/etc/fleet-backup/openclash/<文件名>.<UTC 时间>`（留 7 天、最多 30 份；失败或需人工处理的作业还在用的备份一份不删）→ 只改这个出口代理块里的 server / port / uuid / servername / public-key / short-id 6 行（名字、分组、规则不动；名字带不带引号都认；写法认不出、出口现在不指向旧入口、改动行数不对都一行不写）→ 重启 OpenClash → 经 mihomo 测这个出口的延迟（同采集，各试 3 次）。重启失败、API 不起来、测不通：这台自己换回备份，之前改好的也按各自的备份换回，作业失败，编号不动。凭据（uuid、公钥、short-id）只在中控与路由之间，作业日志、审计里只有出口名与 server:port。团队1 旁路由（team2 那台）上的看门服务会用模板重生成配置，但它以当前配置为准、会自动写回模板，不用特殊处理。
   - **交换编号**：同 `fleetctl rename` 的那套规则与审计（`machine.rename`），旧节点先挪开、新节点再接旧编号；新节点原来的团队压缩编号（同退役）。旧节点同「退役」的默认去向：进备用团队（记下原名），由「到期满 1 天自动回收」接手（§2），要留就续费或移出备用团队。
4. 失败后 `fleetctl retry <job>`：从失败那一步重来（改路由那一步失败时路由都已换回，重试从头改）。只能在开始改路由之前取消（排队中，或改路由失败停在第一步时）；之后只能重试到完成。错误里写「换回失败、需要人工处理：<路由>（…，备份 …）」时那台路由的配置停在改了一半：作业不能取消，按备份换回或把出口改好（`fleetctl ssh <路由>`）后重试。
5. 新节点的分享链接本来就和旧的不同：没有经软路由、直接用旧分享链接的客户端要换成新节点的链接（`fleetctl share 团队2-01`）。用客户端订阅（§20）的客户端下次更新订阅就是新节点，不用手改。

### 换线路机（节点换到另一台线路机）
1. `fleetctl move 团队1-06 --to 线路机3`（交互确认）或加 `--yes --follow`。节点必须在用，且只有一个在用入口（有多个用 `--from 线路机2` 指定换掉哪条）。
   **几个节点要换到同一台线路机时用一条批量命令**：`fleetctl move 团队1-02,团队1-05,团队1-07 --to 线路机3 --yes --follow`（逗号分隔；`--from` 对每个节点都适用）。各节点一个作业，同搬空一样都验收完新入口后由一个「带头」的一起改软路由：每台路由只改一次、OpenClash 只重启一次（逐个 move 时同一台路由每换一个节点就重启一次、客户断线一次，10-24 团队1 旁路由因此断了 6 次）；失败、取消、重试、需要人工处理的行为同搬空（下一节）。预览里有一个节点不能换就一个都不提交，先处理或把它去掉。网页：线路机抽屉概览的入口表勾选几个节点 →「换到…」。
2. 作业先在目标线路机建新入口（新端口、新凭据），节点是 VPS 节点时同时把新线路机 IP 加进节点防火墙放行名单（nft 表，节点上 ufw / firewalld 在运行时一并放行，见 §3）；新入口应用完、出口探测通过之后才摘旧入口，最后把旧线路机 IP 从放行名单拿掉。换线期间节点始终有一个可用入口，不断网。
   旧入口是穿透的，新入口也是穿透（目标线路机 agent 太旧时按普通建，日志 warn）：建好后节点的 bridge 加上新隧道并重启（旧入口经隧道的连接断开几秒，紧接着改软路由本来也要断），最后一步把旧隧道从 bridge 配置里去掉（不重启）。
3. **入口的线路机和端口都会变**：预览与提交结果列出换走的入口（原线路机:端口），`--follow` 完成后列出「原入口 → 新入口」。用客户端订阅（§20）的客户端更新订阅后自动换上新入口；用分享链接的要换：`fleetctl share 团队1-06` 取新链接发给客户端，旧链接失效。网页上作业完成的通知里有「复制新分享链接」。
4. 想中止：摘旧入口之前 `fleetctl cancel <job>`，新入口被摘除、防火墙恢复，旧入口不动。摘了旧入口之后只能 `fleetctl retry` 到完成。旧线路机不在线时「等待旧线路机摘除」会失败，线路机恢复后重试。

### 搬空线路机（线路机退役前）
`fleetctl evacuate 线路机2 --to 线路机3 --yes --follow`：为线路机上每个在用入口的节点各建一个换线路机作业。各作业并行建新入口、验收，都验收完后由其中一个（作业日志写「带头」）把同批全部节点的软路由出口一起改：每台路由只改一次、OpenClash 只重启一次（会断开它上面全部连接，预览写明「软路由 X 的 N 个节点的出口一起改，OpenClash 重启 1 次」，搬之前告诉客户）。任何一台路由改失败，已改的全部换回、各节点的旧入口都不摘，同批作业一起失败；修好后把失败的都点重试，照样一起改。被带头的认领之后跟着的作业不能取消，等它做完；带头的改回失败要人工处理时，跟着的也显示「需要人工处理」，先处理并重试带头的那个，它改完之后再重试别的。中途失败停着、之后单独重试的节点自己改（同单独换线路机）。入口停用/还在应用中、节点有别的作业的会列为「跳过」，处理后再搬一次。全部搬完（旧入口 removed）后才能 `fleetctl retire 线路机2 --now`（线路机不属于团队，只能立即回收；有节点入口时会被拒绝，并提示先搬空）。线路机自己的直出入口不搬也不挡退役：退役作业把它一起摘掉，用它的客户要换到别的线路机的直出链接。

### 退役与回收站
生命周期只有一条路：在用 →（退役 = 进备用）→ 订阅过期满 1 天 → 清理 → 回收站。「立即回收」走同一条路，只是不等到期。
1. **进备用**（`fleetctl retire <机器> --reason … --yes`，网页退役对话框默认选项）：一个事务，不建作业。改到备用团队最小的空号（同 `rename`：审计、线路机备注刷新），记下原名和退役时间，原团队编号前移；宿主机上的同机 IP 节点一起进。机器照常运行，入口、端口、软路由出口都不动，告警照常通知。
2. **撤销**：移出备用团队就行（`fleetctl rename 备用-03 --team 团队1`），不用重新上架，退役标记一并清掉。旧的「恢复已退役机器」已经删掉。
3. **软路由**不会自动改：退役预览和到期提醒里列出还指向它的出口（备用机器只在还有出口指向它时才发到期提醒，没有出口指向的不提醒、不算进「即将到期」）；要客户无感地换掉，在它进备用期间先 `fleetctl replace`。出口还指着它（备用宿主机含它上面的同机 IP 节点）的备用机器到期也不自动回收（回收会摘入口、客户的出口跟着断），先 `fleetctl repoint` 改指向，或确认后 `retire --now`；宿主机上还有在用（不在备用团队）的同机 IP 节点的也不自动回收，也不算闲置备用（宿主机断了它们跟着断）：告警与续费提醒照常，先退役或换走这些 IP 节点；手动把宿主机改进备用团队时随行的 IP 节点与退役一致，带走所有不在备用的。取消指向（或 IP 节点都走了）后它就是闲置备用，已发过触发的告警会收到一条「没有软路由出口指向（闲置备用），不再告警」的恢复。
4. **到期回收**（中控每小时）：备用团队里在用、有订阅、过期满 1 天的发起退役作业（同 `--now`，操作人「系统」），完成时移进回收站。上架取消的、这一版之前就退役了的机器由同一个维护任务直接收进回收站（中控启动时先跑一轮：升级部署后几秒内生效）。
5. **立即回收**（`--now`）：线路机、没有订阅的、已过期满 1 天的、上架中 / 上架失败的、已经在备用里的只能这样。退役作业：摘入口 → 等线路机 → 清理（`--no-cleanup` 跳过；连不上就跳过登录清理，入口照摘、令牌照撤）→ 撤令牌 → 完成时同一个事务移进回收站。
6. **回收站**（`fleetctl recycle ls / show`，网页机器页的「回收站」）：只读，一行一台：退役前的名字与团队、回收时的名字、IP、供应商与套餐、价格周期、上架 / 退役 / 回收时间、原因、流量合计，以及回收时的快照（续费记录、入口历史、出站参数，不含秘密）。不受保留期清理影响。机器行连同遥测、入口由中控在不再被线路机统计用到后自动物理删除（最多约 93 天），用户看不到、也不用管。
7. **旧面板的退役机器**：运维从旧库只读整理出 JSON（`source_id` 用旧面板资产 uuid，没有就「供应商:service_id」；格式见 API.md「退役与回收站」），先 `fleetctl recycle import --file legacy.json` 预演，把会导入、会跳过的名单给用户确认，再加 `--yes`。同一个 `source_id` 重复导入只有一行；IP 或供应商编号对上面板里还没回收的机器的会跳过并说明。

### 穿透入口（节点主动连线路机，DESIGN.md §4「穿透入口」）

**什么时候用**：节点的供应商丢「外面新发起到节点」的连接（入站 SYN），节点自己往外连没问题——表现是客户隔一会转圈 1–3 秒、`fleetctl show <节点>` 的 TCP 探测有 SYN 重发（`retrans`）或偶发不通而出口正常；供应商的原话常是「当没公网 IP 用、直接穿透、出站没问题」。可以先在节点上自测：`fleetctl exec <节点> -- 'for i in $(seq 50); do timeout 3 bash -c "</dev/tcp/1.1.1.1/443" || echo fail; done | grep -c fail'`（出站几乎不失败），再从线路机连节点的 SS 端口对比。新上架的节点默认就是穿透（`fleetctl settings entry-mode` 看、改；没设过是穿透）；存量入口不会自动切换。

**开启**：
1. 线路机与节点的 agent 要是这一版的（会穿透）：预览说「agent 版本过旧」时先 `fleetctl upgrade-agent <线路机或节点> --yes --follow`。
2. `fleetctl entry reverse <入口或节点> --on` 看预览（会在节点上装 bridge 连哪个地址、线路机不重启 Xray、节点上别的穿透入口要不要跟着重启 bridge）；确认后加 `--yes --follow`。网页：入口的「⋯」→「开启穿透…」。
3. 作业三步：推 bridge 并启动 → 切换并经入口验收出口 IP → （开启时跳过）收起 bridge。验收不过中控**自动切回普通模式**、作业失败，错误写明原因；查清后 `fleetctl retry <作业>` 从切换那一步重来，或 `fleetctl cancel <作业>`（补偿收起 bridge）。
4. 这个入口上正在进行的连接会断开一次（客户端自动重连），线路机上别的入口不受影响；分享链接、订阅、软路由出口都不变。

**验证**：`fleetctl entries <节点>` 的「模式」是「穿透」、TCP 一格是节点 → 线路机的建连延迟（节点 agent 升级后才有，旧版本显示「-」）、出口「通」；`fleetctl exec <节点> -- 'systemctl is-active fleet-xray-bridge; journalctl -u fleet-xray-bridge -n 20 --no-pager'`；`fleetctl exec <线路机> -- '/usr/local/bin/xray api lso --server=127.0.0.1:62789 | grep rvs-'`（有 `rvs-<入口>` = 隧道挂上了）。客户那边新连接不再转圈。

**切回普通**：`fleetctl entry reverse <入口> --off --yes --follow`：线路机改回连节点的 ssserver（一直留着，防火墙照旧放行），验收通过后节点上没有别的穿透入口就停掉删掉 bridge（xray 程序留着）。入站丢包的问题会回来。

**出问题时**：
- 穿透入口的 TCP（`fleetctl entries` 的 TCP 列、抽屉「TCP 延迟」图卡写「节点 → 线路机」）是节点 agent 主动连线路机入口端口量的（读 /etc/fleet-bridge/xray.json，每 30 秒），只画图、不告警：它不通 = 节点连不上线路机入口（线路机入口端口被挡、节点出站被挡），隧道也就挂不上，同时会有 `egress_fail`。切换模式前后同一条曲线口径不同（前普通 = 线路机 → 节点）。
- 穿透入口告警 `egress_fail`：隧道断了或节点出不去。线路机报隧道缺席满 30 秒时中控会自动叫节点 agent 重启 bridge（节点 agent 日志「中控发现穿透隧道没挂上，已重启 fleet-xray-bridge」），一般 1 分钟内恢复；没恢复看 bridge 日志（连不上线路机入口？节点出站被挡？）。轮换凭据、停用后再启用的穿透入口也会这样断约 1 分钟，等它自动恢复。
- 手动重启 bridge（修改状态，先确认）：`fleetctl exec <节点> -- 'systemctl restart fleet-xray-bridge'`——断开这台节点上全部经隧道的连接约 2 秒。
- 改过线路机的 REALITY 参数或 IP（手工改库）后，对其上的穿透入口 `--off` 再 `--on`（bridge 的配置要重推）。
- 同机 IP 节点、家宽代理不支持穿透（预览里写明；上架、加入口时自动按普通建）。

### 同机 IP 节点（一台 VPS 节点上的多个 IP）
供应商给一台 VPS 节点加了 IP 时，每个附加 IP 上架成一台独立的节点（自己的团队编号、入口、出口 IP），按 IP 计节点：
1. 先在供应商那边把 IP 直接配到这台机器的网卡上（`ip -4 addr` 看得到）；从这个 IP 发出的流量对外显示的要是它自己（作业第一步会用 `curl --interface` 访问中控自动核对）。
   **1:1 NAT 映射的 IP**（公网 IP 不在网卡上，供应商把它的全部端口转到网卡上的某个内网地址，例如 ens19 的 10.116.0.67 ↔ 209.240.166.50）也可以：宿主机上先配好这个内网地址和策略路由（`curl -4 --interface 10.116.0.67 https://api.ipify.org` 要返回公网 IP），照常用公网 IP 上架。上架检查与作业第一步发现公网 IP 不在网卡上时，会让每个本机 IPv4 各访问一次中控 `/echo`，回显正是这个公网 IP 的那个本机地址记为它的「本地地址」（`show` 与机器抽屉里显示）：ssserver 监听并从它出站，线路机、入口仍连公网 IP。一个都对不上（或有几个都对上）时检查失败并列出各本机地址出去的 IP。
2. `fleetctl provision --kind vps --host <宿主机> --ip <新 IP> --team 团队1 --relay 线路机2 --yes --follow`（批量文件条目写 `"host"`）。不用填 SSH 端口、密码、SS 端口：作业用中控密钥登录宿主机，先核对 IP（不在网卡上、或经它访问中控回显的来源不是它都会失败并说明原因），再在宿主机上装它自己的 ssserver 实例 `fleet-ssserver@<端口>`（端口 8389 起由中控分配，从这个 IP 监听和出站）和防火墙表 `ss_guard_<端口>`，然后建入口、验收。宿主机原来的 ssserver 与防火墙不动、不重启。
3. `show <宿主机>` 列出「同机 IP 节点」，`show <同机节点>` 显示「宿主机」。它没有自己的 agent：在线状态、主机读数、曲线都是宿主机的，`upgrade-agent` 升级宿主机即可。供应商取宿主机的；费用默认不记（附加 IP 单独收费时在它的「费用」里填），宿主机的流量额度把它的流量算进去。
4. 单独退役同机节点（没有订阅时只能 `--now`）只删它自己的实例；**宿主机进备用、立即回收时同机节点一起走**（`retire` 会先列出来）。物理删除时宿主机等它的同机节点先删（中控自动按这个顺序）。
5. 只想下线宿主机自己的 IP、保留机器：本期不支持；可以停用宿主机的入口（`fleetctl entry disable …`），它的「没有在用的入口」告警可静默。
6. 同机 IP 节点随迁移 0019 引入：装上这一版后不能直接换回更早的中控（旧版看到它不认识的迁移会拒绝启动，见 §9），出问题只能修好再发版，或按 §10 从备份恢复。

## 7. 版本升级顺序
先升中控（`lab/deploy-server.sh` 就是先装 fleet-server、再把新 agent 放进 dist），再 `fleetctl upgrade-agent --all --yes` 升 agent：新 agent 的上报可能带旧中控不认的字段形状（如容器里 `load1` 为 null），旧中控会拒收整份上报。
探测口径修正（迁移 0038）两边都兼容，仍按这个顺序：新中控收旧 agent 的上报照常（没有 `retrans`，卡片读数已改成近 1 小时中位数，SYN 重发尖刺不再左右它）；新 agent 报的 `retrans` 旧中控忽略。线路机的心跳格改由中控探（`relay_reach`），只要中控升级就生效。
反过来，期望状态里的新东西旧 agent 也不认：直出入口（出站 `direct`）要等那台线路机的 agent 升级后再建，否则线路机报「agent 版本过旧」、整台的配置停在旧代数（这时升级 agent，或取消那个新增入口作业把直出入口摘掉，都能恢复）。
穿透入口（出站 `reverse`）由中控把关：线路机与节点的 agent 都报过会穿透（`Report.caps`）才能开，旧 agent 时开关被挡、上架 / 加入口自动按普通建（作业日志 warn），不会把旧线路机的配置弄坏。所以上线顺序是：先备份库（迁移 0093，见 §9 回滚）→ 部署中控 → `fleetctl upgrade-agent --all --yes` → 之后新上架的才按默认的穿透建；存量入口挑着 `entry reverse --on`。
中控改了期望状态的生成逻辑（加字段、改算法），而库里的数据没变时，线路机不会自己重拉：改的人要把 `db::DESIRED_FORMAT` +1，新中控启动时和库里记的（app_setting `desired_format`）不同就给所有未退役线路机代数 +1，日志里有一行「期望状态格式版本变为 n」。

### 升级 agent：金丝雀与回滚
- **顺序**：`--all` 不是一起升。先升一台做金丝雀（有线路机先挑线路机，同类里在用入口少的先上），它成功了其余线路机一台接一台，线路机都成功后 VPS 节点并发（同时最多 `job_workers` 台）。命令输出第一行后面就是这次的顺序（金丝雀是哪台），作业按执行顺序列出；`--follow` 依次跟着看。排在后面的作业在前一台结束之前一直是「排队中」：排队中的可以取消（`fleetctl cancel <作业>` 或网页作业详情），「全部升级」里等它的跟着取消；已经开始的不能取消（推送、重启到一半中断更危险），等它结束。
- **每台的回滚**：推送前旧程序留成同目录的 `/usr/local/bin/fleet-agent.prev`（成功后也留着，下次升级覆盖；退役清理一并删）。新版本重启后 3 秒内主进程就退出（起不来），或 2 分钟内没有以新版本号上报，作业自动把 .prev 换回去并重启 agent，然后失败，错误写「新版本 X …，已回滚到 <旧版本>」：这时机器已经回到旧版本、照常上报，不用动它。
- **线路机还要查 Xray**：新版本自己报的 Xray 状态要做到——Xray 在跑、已应用的配置追上升级开始时的代数、没有应用错误（中控记的与 agent 自报的都算）；2 分钟做不到同样换回旧版本并失败，错误写「线路机检查没通过（Xray 没在跑；…）」逐项列出。只查升级前就做到的项（升级前 Xray 就没在跑、配置没应用到最新、有应用错误的，那一项不查），要查哪几项见推送那一步输出的「升级后检查」。换回旧版本后，旧 agent 启动时按原来的配置重新应用一遍；之后 Xray 仍不正常就按告警处理。所以新版本让 Xray 不在跑、配置应用不上或应用出错时，金丝雀就被换回、其余线路机不再升级，不会一台接一台弄坏；这几项查不出的问题（Xray 照常，但流量统计、探测出了错）仍可能逐台带到所有线路机，升级后看一眼告警与读数。
- **停在半路**：金丝雀或任何一台线路机换上新版本后出问题（起不来、没上报、线路机检查没通过），没开始的作业全部取消（错误写明是哪台），已经升好的不动。推送之前就失败的（SSH 连不上、登录被拒、推送失败：机器上的程序没换过，与新版本无关）只算那一台，后面的照常继续；这样失败的金丝雀不算验证过，下一台线路机就是实际的金丝雀。先查原因：失败作业的错误、`fleetctl logs <机器> --unit fleet-agent`。修好（多半是换一个 agent 版本、重新部署中控）后再 `--all` 一次：已经是新版本的机器推送跳过，只轮换令牌、重启 agent。VPS 节点之间互不等待，一台失败只影响它自己。
- **中途重新部署了中控**：`--all` 发起时记下 dist 里 agent 的 sha256 与版本号，每台推送前核对。中途换了版本，没开始的都取消、正要推送的失败，错误写「中控上的 agent 在升级过程中换了版本（发起时是 X），请重新发起全部升级」：照做，新的 `--all` 按新版本从金丝雀重来。中控上没有 agent 程序（或读不出版本号）时 `--all` 直接报错，不建作业。
- **重试**：失败的升级作业可以 `fleetctl retry <作业>`，从推送重来（不是只重等上报）；线路机检查沿用第一次换程序之前记下的升级前状态。
- **回滚也失败**（错误里写「需要人工处理」：机器上没有 .prev，或换回去旧版本也没起来）：agent 可能没在运行，这台会报 agent 离线。看日志找原因后手动换回并重启（修改状态，先确认）：
  ```
  fleetctl exec <机器> -- 'ln -f /usr/local/bin/fleet-agent.prev /usr/local/bin/fleet-agent.r && mv -f /usr/local/bin/fleet-agent.r /usr/local/bin/fleet-agent && systemctl restart fleet-agent'
  fleetctl show <机器>        # agent 版本与在线
  ```
  没有 .prev 时只能先让中控 dist 里是能用的 agent（修好后重新部署中控），再重试这个作业。

## 8. PostgreSQL 参数建议
发行版默认值（`shared_buffers = 128MB`、`work_mem = 4MB`）对中控偏小，建议在中控机上调：

| 参数 | 建议 | 原因 |
|---|---|---|
| `shared_buffers` | 内存的 25% 左右（4 GB 内存给 1GB） | 原始时序表（主机样本每台每 10 秒一行、探测、访问记录）的当天分区和小时汇总表是一直在读写的热数据，放得进缓存时曲线查询、每 3 秒一次的实时视图不用反复读盘 |
| `work_mem` | 16–32 MB（4 GB 内存取 16MB） | 每 5 分钟的主机小时汇总要把当前小时的全部样本按（机器, 时间）排序算网卡增量：实验室 136 台、约 6 万行，4MB 时排序落盘约 5 MB 临时文件；机器详情的长时段曲线（按分钟 / 小时分组聚合）同理。它按每个排序 / 哈希节点各算一份，连接池上限 20 条，不要给太大 |
| `wal_compression` | `lz4`（默认 off） | WAL 里近八成是整页镜像：每次 checkpoint 之后某一页第一次被改，整页写进 WAL。中控一直在写的页（当天分区、小时汇总、agent 状态等）每个 checkpoint 周期都要各来一次。lz4 压缩整页镜像，CPU 开销很小；实验室平均每个整页镜像从约 5.8 KB 压到约 2.6 KB |
| `checkpoint_timeout` | `15min`（默认 5min） | 整页镜像每个 checkpoint 周期重来一遍，周期拉长后热页的整页镜像次数少很多（实验室同样 15 分钟从约 8100 个降到约 3400 个）；代价是崩溃后恢复要多重放一些 WAL（实验室一个周期约 22 MB，秒级） |
| `max_wal_size` | `2GB`（默认 1GB） | 两次 checkpoint 之间 WAL 攒到这个量就提前做 checkpoint（又带出一轮整页镜像）；留足余量，批量上架、agent 补传积压时也按 15 分钟一个周期走。平时 pg_wal 只占一两个周期的量 |

改法（`psql` 以超级用户执行）：`alter system set work_mem = '16MB'; select pg_reload_conf();` 立即生效；`alter system set shared_buffers = '1GB';` 要重启 PostgreSQL 才生效（fleet-server 的连接池会自动重连，正在进行的请求会失败一次）。改完用 `show work_mem;`、`show shared_buffers;` 确认。

WAL 三项由 `deploy/central/install.sh` 写进 `/etc/postgresql/<版本>/main/conf.d/fleet.conf`，`systemctl reload postgresql` 生效，不用重启；确认：`select name, setting, sourcefile from pg_settings where name in ('wal_compression', 'checkpoint_timeout', 'max_wal_size');`（用 `alter system` 改过同名参数的话 `postgresql.auto.conf` 优先，先 `alter system reset <参数>`）。实验室实测（fleet 库约 1.4 GB，用 pg_waldump 按库统计，排除测试库）：改前每 5 分钟约 20 MB、整页镜像占 78%，合 66 KB/s（约 5.5 GB/天）；改后每 15 分钟约 22 MB、整页镜像占 40%，合 25 KB/s（约 2 GB/天），少了约 63%。

## 9. 生产中控：部署与回滚

部署 / 升级：本机在 `v1/` 下运行 `deploy/central/deploy.sh <中控 ssh 主机> fleet.kismet613.com`（幂等，首次安装也用它）。中控 ssh 主机写本机能直接 `ssh` 的名字：`~/.ssh/config` 里配了别名（如 `debian13`）就用别名，没有就写地址 `185.13.159.131`。

### 编译主机：fleet-dev 或 docker

deploy.sh 与 `lab/sync-server.sh`、`lab/deploy-server.sh`、`lab/install-fleetctl.sh` 都经 `lab/build-lib.sh` 选编译主机，两种方式：

| | lab（默认） | docker |
|---|---|---|
| 在哪编 | 家里实验室的 fleet-dev（`ssh -F ~/.ssh/fleetlab_config fleet-dev`），rustup 工具链，源码 `/root/src` | 任意一台能 ssh、有 docker 的 Linux（可以 rootless、无 sudo、不装 Rust），如办公网的 dev 机；源码在 `FLEET_BUILD_DIR`（默认 `~/fleet-v1-dev/src`） |
| fleet-server | glibc 版，`target/release` | `rust:1.98.1-slim-trixie` 里编 glibc 版（中控是 Debian 13），缓存卷 `fleet-v1-cargo-gnu`，`target-gnu/release` |
| fleet-agent、fleetctl | musl 静态，`target/x86_64-unknown-linux-musl/release` | `rust:1.98.1-alpine` 里编 musl 静态，缓存卷 `fleet-v1-cargo`，`target/release` |
| xray、ssserver、geoip.dat 来源 | fleet-dev `/opt/fleet/dist`（必须有） | 编译主机上的 `FLEET_BUILD_DIST`（默认 `~/fleet-v1-dev/dist`）；三个不全就不带 dist，打一行「dist 不随包」，中控上现有的保持原样 |

fleet-server 不编 musl 版：项目没有自定义全局分配器，musl 自带的 malloc 在多线程服务上慢。两个镜像各用自己的缓存卷与 target 目录，互不覆盖产物。版本号的提交哈希两种方式都经环境变量 `FLEET_GIT_HASH` 交给 cargo。

选 docker：设环境变量，或写本机文件 `v1/lab/build.env`（已在 .gitignore 里，不进仓库；每行 `KEY=value`，只认 `FLEET_BUILD*`，不执行其中的代码；两处都有时环境变量优先）。什么都没配就是 lab，行为与以前一样。

```
# v1/lab/build.env（或同名环境变量）
FLEET_BUILD=docker
FLEET_BUILD_HOST=10.172.17.213        # ssh 目标，可写 user@host 或别名；写 wsl 则用本机 WSL（Windows Git Bash，
                                      # 发行版 FLEET_BUILD_WSL_DISTRO，默认 archlinux，里面装 docker 即可），不压 PVE
# 以下可选，括号里是默认
# FLEET_BUILD_DIR=fleet-v1-dev/src     远端源码目录（相对远端家目录）
# FLEET_BUILD_DIST=fleet-v1-dev/dist   远端 dist 来源
# FLEET_BUILD_MUSL_IMAGE=rust:1.98.1-alpine   FLEET_BUILD_GNU_IMAGE=rust:1.98.1-slim-trixie
# FLEET_BUILD_MUSL_CACHE=fleet-v1-cargo       FLEET_BUILD_GNU_CACHE=fleet-v1-cargo-gnu
# FLEET_BUILD_DOCKER_ARGS=--network fleet-v1-dev -e FLEET_TEST_DB=postgres://fleet:fleet@fleet-v1-pg/fleet_test
#                                      docker run 的附加参数：lab/sync-server.sh 在 musl 容器里跑集成测试要连库时
```

用法：

```
FLEET_BUILD=docker FLEET_BUILD_HOST=10.172.17.213 deploy/central/deploy.sh --dry-run 185.13.159.131 fleet.kismet613.com   # 先演练
FLEET_BUILD=docker FLEET_BUILD_HOST=10.172.17.213 deploy/central/deploy.sh 185.13.159.131 fleet.kismet613.com
FLEET_BUILD=docker FLEET_BUILD_HOST=10.172.17.213 lab/sync-server.sh 'cargo test -p fleet-server --lib'                 # 编译主机上跑测试
```

- `--dry-run`（或 `FLEET_DEPLOY_DRY_RUN=1`）：照常同步、编译、拉回二进制、构建前端、打包，但不连中控（dist 按全部带上算），包存到本机临时目录、列出内容就退出。改了部署脚本、换了编译主机先用它看一遍包里有什么。
- `lab/deploy-server.sh` 在 docker 方式下也是在编译主机上编，编好的三个二进制连同 `deploy/` 经本机传到 fleet-dev 的 `/root/fleet-prebuilt` 再装（装完即删 `/root/fleet-prebuilt`，中途失败留着便于排查，`lab/cleanup.sh` 会清掉），部署目标仍是实验室中控 fleet-dev；`lab/deploy-web.sh` 的前端总在本机构建，不经编译主机。
- 本机是 macOS 时，自带的 tar 会把扩展属性写成 `._*` 文件打进包里（进了 `migrations/` 会让 `sqlx::migrate!` 编译失败）。各脚本统一经 `fb_tar` 打包：`COPYFILE_DISABLE=1`，bsdtar 再加 `--no-xattrs`（GNU tar 不加）；远端解包后再删一遍 `._*` 兜底。手工打包也照这样做。
- 核对装上的版本：`/opt/fleet/fleet-server version`、`/opt/fleet/dist/fleet-agent version`，都是 `0.1.0+<提交哈希>`；install.sh 最后一行同样打出 fleet-server 与 agent 的版本。

### 部署要点


- `Cargo.toml`、`Cargo.lock`、`crates`、`migrations`、`deploy`、`web`、fleet-ops 技能（仓库 `.claude/skills/fleet-ops`）有未提交的改动时拒绝部署。
- 每次还装中控本机的 `/usr/local/bin/fleetctl`，健康检查通过后跑 `fleet-server local-admin`（建或修复全权密钥 central-local，仍有效不换），写 `/root/AGENTS.md`、`/root/CLAUDE.md` 与 `/root/.claude/skills/fleet-ops/` 下的 `SKILL.md`、`json-fields.md`（§14）。部署最后一行写「本机 fleetctl apikey:central-local」说明能用。
- 版本号 `0.1.0+<哈希>` 里的哈希是最后一次改动 `Cargo.toml`、`Cargo.lock`、`crates`、`migrations`、`deploy` 的提交：只改前端或文档的提交不换哈希，编译主机上不重编 server 和 agent。
- xray、ssserver、geoip.dat 先和中控 `/opt/fleet/dist` 比 sha256，相同的不上传，中控上的保持原样（docker 编译主机上没有 dist 来源时整个不带，见上）。
- 编译失败、或 install.sh 重启后等 60 秒未登录访问 `/api/v1/auth/me` 仍不是 401、或首页 `/` 不是 200 text/html（前端没挂上，多半是 `/opt/fleet/web` 对 fleet 用户不可读），部署以非 0 退出，前者会打出 fleet-server 最近 60 行日志。中控上的安装包无论成败都删掉。
- 安装顺序：会失败的预检（软路由隧道的 23000–23999 端口与 `sshd -t`）最先做，要换的 fleet-server、fleetctl、dist、前端先放成 `.new`，紧挨着重启 fleet-server 之前才一起换上：预检或中间任何一步失败，线上的二进制、前端、dist 原样不动（不会出现旧进程配新前端，也不会让磁盘上的新二进制在之后一次崩溃重启时无人值守地升级、跑迁移）。重启之后的步骤（Caddy、健康检查）失败时新版已经在跑，回滚见 §9。
- install.sh 在中控的临时 systemd 单元 `fleet-install` 里跑（`systemd-run --wait --pipe --collect`）：本机 ssh 断了或 Ctrl-C，安装继续跑完；输出同时写 `/root/fleet-install.log`（断线后 `tail -f` 看进度，成功时最后一行是「fleet-server … api=401 …」，否则是失败原因）。上一次的安装还没结束时再部署会直接报错退出，不会另起一个。
- 换下来的旧版本留在中控：fleet-server 在 `/opt/fleet/fleet-server.prev`，前端在 `/opt/fleet/web.prev`，agent 在 `/opt/fleet/dist/fleet-agent.prev`（各自内容相同的重复部署不覆盖它们；只留上一版，geoip.dat、xray、ssserver、sing-box 不留）。
- fleet-server 的二进制与 systemd 单元都和线上逐字节相同时（纯前端发版：前端按请求从 `/opt/fleet/web` 读，换目录即生效）install.sh 不重启 fleet-server，不做上线前备份，其余照常（换前端并留 `web.prev`、健康检查）；二进制或单元变了、首次安装、或 fleet-server 没在跑时照常重启。
- 换上新版之前，install.sh 先同步做一份备份（`systemctl start fleet-backup`，等它做完；备份失败部署就停在这里，线上的版本、前端、dist 原样不动）：这是上线前的回滚点，不用再手动 `systemctl start fleet-backup`，也不用手工在 `/root/pre-deploy-*` 里存。首次安装（中控上还没有 fleet-server、库是空的）跳过这一步，装完后照旧再做第一份；fleet-server 二进制没变（没有新迁移）时也跳过。备份目录按「每个北京日期最后一份 + 最新 3 份」轮换（见 §10），所以部署前这份至少会保留到之后又有 3 份新备份；要长期留着的回滚点另存。已有的 `/root/pre-deploy-*` 是历史回滚点，不动。
- 迁移 0029 先把币种去空白转大写，再给套餐 / 订阅 / 续费记录的币种（3 个大写字母）和通知渠道种类（当时是 telegram / wecom / webhook）加约束；存量里还有不合规的不让迁移失败，日志里有「0029：… 暂不验证」的警告。看到时查出那几行（如 `select id, currency from plan where currency !~ '^[A-Z]{3}$'`）改成正确的币种，再 `alter table plan validate constraint plan_currency_iso`（订阅 / 续费记录 / 渠道同理：`subscription_currency_iso`、`renewal_currency_iso`、`notify_channel_kind_check`）。
- 迁移 0093（穿透入口）只给 `entry` 加三列（`mode` 默认 normal、`bridge_uuid` 随机生成、`reverse_kick_at`），存量入口一律普通模式，不改任何行为。新迁移照 §9 回滚的规矩：上线前要有备份（install.sh 换版前自动做）。
- 迁移 0098 把旧的逐节点 `init` 增减记录（每个节点一条）按团队合并成一条（节点名单进 `detail.nodes`），并给 `billing_slot` 加 `vacate_reason`（空出原因）：现有空出 / 已结束的系统名额按「现在」的不计费状态回填一次（近似），之后由对账在空出时落库。上线前的备份由 install.sh 自动做。
- 迁移 0081 把通知渠道种类约束改成只允许 telegram / feishu，并删掉库里已有的企业微信、webhook 渠道（它们排着的待发通知一并删，发送记录里的渠道名置空）；之后在设置页新建飞书渠道。
- 重启时 fleet-server 优雅退出：不再领新作业，正在跑的步骤做完就停在两步之间（最多等 60 秒，没做完的重启后从这一步重做），这期间接口照常；之后先通知线路机的期望状态长轮询（回 204）和实时流 WebSocket（以 1012 关闭）收尾，客户端随即重连（重启空窗内按退避重试），再停止接新连接，进行中的请求最多再等 10 秒。有作业在跑时一次重启最多约 70 秒才换上新版本。systemd 单元是 `KillMode=mixed`、`TimeoutStopSec=90`：停止时 SIGTERM 只发给 fleet-server 主进程（不是同时发给它正在用的 ssh 子进程，否则进行中的步骤当场失败），主进程退出或 90 秒到点后才对残留的子进程发 SIGKILL。步骤里 ssh 超过 60 秒没做完的照旧被打断、重启后重做。
- fleet-server 启动时先占端口再碰库：手动再起一个 `fleet-server serve` 会因端口被占直接退出，不会动在跑实例的作业。
- 启动时（之后每小时）删过期分区前核对本机时钟：任何一张分区表最近一天里有数据（agent 每 30 秒报主机读数）就按本机时钟删，某张表（如访问记录）空闲多久都照期限删；所有表都没有最近一天的数据（开机时钟大幅超前，或整个中控很久没收到上报）时，按各表自己最新的数据减保留期删（以数据为锚，时钟超前也不会把保留期内的整批删掉），日志里是 warn「分区表最近一天都没有新数据…」；表里没有数据的不删。

回滚（新版起不来，或上线后有严重问题）：

1. 先确认这次部署**没有新迁移**：`git diff --name-only <旧哈希> <新哈希> -- migrations` 为空（新旧哈希见中控 `journalctl -u fleet-server | grep 监听 | tail -2`；当前与换下来的二进制也可直接 `/opt/fleet/fleet-server version`、`/opt/fleet/fleet-server.prev version` 看，早于这个子命令的旧版本会打用法）。fleet-server 启动时自动跑迁移；新迁移一旦执行过，旧版本发现库里有它不认识的迁移会拒绝启动，这时不能直接换回，只能修好再发新版本（或按 §10 从备份恢复，丢失备份之后的数据）。
   - **迁移 0055（`incident.engine`）之后**回退到更早的版本（如 627d929），必须连库一起恢复成部署之前的备份，不能只换二进制：0055 给告警表加了不能为空、没有默认值的 `engine` 列，「开着的只有一条」的唯一索引也换成了带 `engine` 的。旧版本本来就会因为不认识的迁移拒绝启动；就算手工删掉 `_sqlx_migrations` 里的记录让它起来，它写告警不带 `engine`、按旧的唯一索引去冲突，**所有告警都写不进去**（机器、软路由、探测点、中控自身的都开不出来、不发通知，只有日志里报错，面板上看不出来）。所以含 0055 的版本上线前要有一份备份（install.sh 换版前自动同步做，`journalctl -u fleet-backup -n 5` 确认），要回退就按 §10「从备份恢复」用这一份恢复库、再换回旧版本，备份之后的数据（上报、作业、审计）会丢。之后带新迁移的版本同理：上线前先做一份备份。
2. 没有新迁移时，在中控上换回旧版（先复制再改名：正在运行的可执行文件不能直接覆盖）：
   ```
   cp -p /opt/fleet/fleet-server.prev /opt/fleet/fleet-server.new && mv -f /opt/fleet/fleet-server.new /opt/fleet/fleet-server && systemctl restart fleet-server
   curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/v1/auth/me     # 应为 401
   ```
3. 这样只换回了 fleet-server：前端 `/opt/fleet/web` 和 dist 里的 fleet-agent 还是新的，换回后先别上架、别 `upgrade-agent`（新 agent 的上报旧中控可能拒收，见 §7）。前端和 agent 也要回去时用换下来的 `.prev`（权限与属主随文件保留）：前端 `cd /opt/fleet && rm -rf web && mv web.prev web`；agent `cd /opt/fleet/dist && cp -p fleet-agent.prev fleet-agent.new && mv -f fleet-agent.new fleet-agent`（已经 `upgrade-agent` 推给机器的不受影响，机器上的回滚见 §7）。`.prev` 只留上一版；要回到更早的版本：本机 `git checkout <旧提交>` 后再跑一次 deploy.sh（同样要求没有新迁移）。

## 10. 备份与恢复

中控每天北京时间 03:30 做一份备份（`fleet-backup.timer` → `/opt/fleet/backup/fleet-backup.sh`），放在中控 `/var/backups/fleet/fleet-<北京时间>.tar`（开了加密是 `.tar.age`，见下文「加密备份」），留最近 14 个北京日期、每个日期只留最后一份，另外总是保留最新 3 份（同一天里部署前的同步备份、手动备份不会多占 14 天的名额，也不会被当天后来的备份马上顶掉）；第一次装上时 install.sh 立即做一份，之后每次部署换版前也同步做一份（§9）。手动做一份：`systemctl start fleet-backup`，`journalctl -u fleet-backup -n 5` 看结果。一份 tar 里有：

- `fleet.dump`：`pg_dump -Fc` 整库。`host_metric`、`entry_traffic`、`probe_result`、`access_event` 四张原始时序表（按天分区，只保留几天，量最大）只备结构不备数据，其余表（机器、入口、订阅、作业、审计、告警、小时汇总等）全量。恢复后最近几天的 10 秒粒度曲线和访问明细是空的，小时汇总都在。
- `etc/fleet/`：`secret.key`（库里 SS 密码、REALITY 私钥、通知渠道配置的加密密钥，丢了这些就解不开）、`fleet.toml`、`ssh/id_ed25519`（中控登录所有机器的密钥）。
- `var/lib/fleet/known_hosts`：各机器的主机指纹。
- `etc/ssh/ssh_host_ed25519_key`、`.pub`：中控 sshd 的 ed25519 主机密钥。软路由的隧道按 `/etc/fleet-tunnel/known_hosts` 里存的这把公钥做 `StrictHostKeyChecking=yes`，新机器上主机密钥是新生成的，不放回来所有软路由隧道都连不上。
- `etc/caddy/global.d/`、`etc/caddy/sites.d/`：Caddy 的带外配置（如 `edge-proxy.caddy` 的 PROXY 协议、`http-redirect.caddy`，见 §11）。Caddyfile 本身由 install.sh 重写，不在包里；上面这几样中控上不存在的就不打（备份不会因此失败）。

整个包都是敏感数据：中控上 0640 root:fleet-backup（只有拉取用户能读），PVE 上 0600 root。备份目录本身是 0755：fleet-server 要看得到最新一份的时间，超过 26 小时没有新的就开告警 `central_backup_stale`（§12）。每份旁边有一个 `<备份名>.sha256`（`sha256sum` 格式，备份时算的；明文和加密的都有），随备份一起轮换；PVE 拉取时按它核对。

### 加密备份（可选，推荐）

不加密时中控 14 天（每天一份）、PVE 30 份，每一份都是库 + `secret.key` + 中控 SSH 私钥的明文：任一边被拿到就等于拿到全部。用 [age](https://age-encryption.org) 加密后，两边存的都是密文，私钥只在离线的地方：

1. 在**离线**的电脑上（不是中控、也不是 PVE）生成身份：`age-keygen -o fleet-backup-key.txt`，屏幕上打印的 `Public key: age1…` 是公钥。`fleet-backup-key.txt` 是唯一能解开备份的东西：存进密码管理器 / 打印出来放好，再备一份到别的地方；丢了备份就废了。
2. 把公钥写进中控 `/etc/fleet/backup-age.recipients`（一行一个，可以写多个，如再加一个备用身份；`#` 开头是注释）：`echo 'age1…' > /etc/fleet/backup-age.recipients`。
3. 中控要有 `age` 包：install.sh 已经装（没有才装），老中控跑一次 deploy.sh 或 `apt-get install age`。之后的备份（下次定时或 `systemctl start fleet-backup`）就是 `/var/backups/fleet/fleet-<时间>.tar.age`：tar 经管道直接加密，明文不落盘。PVE 的拉取认得两种格式，加密的存成 `fleet-prod-<时间>.tar.age`（只查 age 文件头和大小，PVE 上没有私钥、解不开）。
4. 确认能解开：把一份 `.tar.age` 拷到离线电脑，`age -d -i fleet-backup-key.txt fleet-<时间>.tar.age | tar -tv` 能列出 `fleet.dump`、`etc/fleet/secret.key`。
5. **开启之前的明文备份还在**：轮换只删最旧的，中控上要再过 14 天、PVE 上 30 天，明文 `.tar`（含 `secret.key` 与中控 SSH 私钥）才会全部轮换掉。确认第 4 步能解开后马上删掉两边的明文：
   ```
   # 中控
   rm -f /var/backups/fleet/fleet-*.tar /var/backups/fleet/fleet-*.tar.sha256
   # PVE
   rm -f /var/backups/fleet-prod/fleet-prod-*.tar /var/backups/fleet-prod/fleet-prod-*.tar.sha256
   ```
   通配符只匹配 `.tar` 结尾的（不会删到 `.tar.age`）；删之前先 `ls` 一遍，确认至少留着一份 `.tar.age`。中控上 `/root/restore` 之类解开过的目录也一并删掉。

关掉加密：删掉 `/etc/fleet/backup-age.recipients`，之后又是明文 `.tar`。换身份：改这个文件即可，旧备份仍要用旧私钥解。

### 家里 PVE 每天取一份

中控上的 `fleet-backup` 用户只能用指定公钥登录，authorized_keys 带 `restrict,command="/opt/fleet/backup/fleet-backup-latest.sh"`：不管请求执行什么都只输出最新一份 tar（请求 `latest+sha256` 时先输出一行「sha256  备份名」），不能开 shell、不能转发端口。authorized_keys 由 root 持有，这个用户改不了。第一次配置：

1. PVE 上生成专用密钥：`ssh-keygen -t ed25519 -N '' -C pve-fleet-backup -f /root/.ssh/fleet-backup`
2. 把 `/root/.ssh/fleet-backup.pub` 的内容放到中控 `/etc/fleet/backup.pub`，再跑一次 deploy.sh：install.sh 看到这个文件才写 authorized_keys，没有就跳过。中控 sshd 配了 `AllowUsers` / `AllowGroups` 的话把 fleet-backup 加进去。
3. PVE 上安装（文件在仓库 `v1/deploy/backup/`）：
   ```
   install -m 755 fleet-backup-pull.sh /usr/local/sbin/
   install -m 644 fleet-backup-pull.service fleet-backup-pull.timer /etc/systemd/system/
   ```
   中控的 SSH 地址不是 `fleet.kismet613.com` 的 22 端口（域名走了 CDN、改过端口）时，改 service 里的 `FLEET_BACKUP_HOST`，或在 PVE 的 `/root/.ssh/config` 里给这个主机配 `HostName`、`Port`。
4. 手动跑一次（第一次连接会记下中控的主机指纹）：`systemctl daemon-reload && systemctl start fleet-backup-pull`，`journalctl -u fleet-backup-pull -n 5` 与 `ls -l /var/backups/fleet-prod` 确认后 `systemctl enable --now fleet-backup-pull.timer`。

之后每天 04:30 左右取一份，存 `/var/backups/fleet-prod/fleet-prod-<北京时间>.tar`（0600），留 30 份。取到的先按中控备份时算的 sha256 核对（明文、加密的都核），对不上不存、服务以失败退出；核对过的校验和存成旁边的 `<文件名>.sha256`，恢复前在那个目录里 `sha256sum -c fleet-prod-<时间>.tar.sha256` 再核一次。PVE 上的拉取脚本要和中控的 `fleet-backup-latest.sh` 一起更新（新拉取脚本遇到旧中控会报「中控没有先给出校验和」；旧拉取脚本遇到新中控照常工作，只是不核对）。取到的和上一份完全一样（中控的备份没更新）时不存、服务以失败退出，`systemctl --failed` 里能看到；去中控 `systemctl status fleet-backup` 查原因。撤销 PVE 的拉取权限：删掉中控的 `/etc/fleet/backup.pub` 与 `/var/lib/fleet-backup/.ssh/authorized_keys`。

### 从备份恢复

在新装（或重装）的中控机上按顺序做：

1. 正常部署一次：`deploy/central/deploy.sh <主机> <域名>`。装好 PostgreSQL、Caddy、fleet 用户、服务与定时器；这时库是空的，密钥是新生成的。
2. 把备份拷到中控并解开：`mkdir -p /root/restore && tar -xf fleet-<时间>.tar -C /root/restore`。加密的 `.tar.age` 在离线电脑上先解成 tar（`age -d -i fleet-backup-key.txt -o fleet-<时间>.tar fleet-<时间>.tar.age`）再拷过去，或把私钥临时拷到中控 `age -d -i /root/key.txt fleet-<时间>.tar.age | tar -xf - -C /root/restore`，用完立刻删掉私钥（`shred -u /root/key.txt`）
3. 停服务、换库（`pg_restore` 以 postgres 执行，从标准输入读，对象属主恢复为 fleet）：
   ```
   systemctl stop fleet-server
   runuser -u postgres -- psql -c 'drop database fleet' -c 'create database fleet owner fleet'
   runuser -u postgres -- pg_restore -d fleet --exit-on-error < /root/restore/fleet.dump
   ```
4. 放回密钥与主机指纹。fleet.toml 用新装的那份（里面的库密码是第 1 步新生成的），备份里 fleet.toml 改过的其它设置（retention 等）对照着抄过来；备份里有 `etc/fleet/ipintel-overrides.toml`、`etc/fleet/backup.pub`、`etc/fleet/backup-age.recipients` 也照样放回：
   ```
   install -m 600 -o fleet -g fleet /root/restore/etc/fleet/secret.key /etc/fleet/secret.key
   install -m 600 -o fleet -g fleet /root/restore/etc/fleet/ssh/id_ed25519 /etc/fleet/ssh/id_ed25519
   install -m 644 -o fleet -g fleet /root/restore/etc/fleet/ssh/id_ed25519.pub /etc/fleet/ssh/id_ed25519.pub
   install -m 640 -o fleet -g fleet /root/restore/var/lib/fleet/known_hosts /var/lib/fleet/known_hosts
   diff /root/restore/etc/fleet/fleet.toml /etc/fleet/fleet.toml
   ```
   备份里有 `etc/ssh/ssh_host_ed25519_key`（以及 `.pub`）、`etc/caddy/global.d`、`etc/caddy/sites.d` 的，也放回去，再重启 ssh 与 caddy（不放回，软路由隧道因主机公钥对不上全断；经边缘机的连接因缺 PROXY 协议配置全断）：
   ```
   install -m 600 -o root -g root /root/restore/etc/ssh/ssh_host_ed25519_key /etc/ssh/ssh_host_ed25519_key
   install -m 644 -o root -g root /root/restore/etc/ssh/ssh_host_ed25519_key.pub /etc/ssh/ssh_host_ed25519_key.pub
   cp -a /root/restore/etc/caddy/global.d/. /etc/caddy/global.d/ && cp -a /root/restore/etc/caddy/sites.d/. /etc/caddy/sites.d/
   sshd -t && systemctl restart ssh && caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile >/dev/null && systemctl restart caddy
   ```
   换 sshd 主机密钥后，人用 ssh 连这台机器会报主机指纹变了（放回备份里的这把就和以前一致，PVE 拉取的第 9 步也就不用做）。
5. 启动并确认：`systemctl start fleet-server`（启动时跑迁移：备份来自旧版本时补上新迁移）；`curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/v1/auth/me` 应为 401。恢复的库里是备份时的 central-local，和第 1 步写进 `/root/.config/fleetctl/config.toml` 的令牌对不上：`/opt/fleet/fleet-server local-admin -c /etc/fleet/fleet.toml` 重建一把（§14），再 `fleetctl status` 看机器。
6. 中控 IP 变了：把域名解析改到新机器。agent 按域名上报，解析生效后自动恢复；Caddy 自动签证书。
7. 放回了 `etc/fleet/backup.pub` 的，再跑一次第 1 步的 deploy.sh：install.sh 看到这个文件才写拉取用户的 authorized_keys，不重跑 PVE 就一直拉不到。
8. agent 令牌：每次装 / 升级 agent 都会换令牌、撤销旧的。备份之后升级过 agent 的机器，机器上的令牌在恢复的库里不存在，上报一律 401（线路照常通，但上报、配置下发都停了）。解析生效几分钟后 `fleetctl ls` 里 agent 一直离线的那些，逐台 `fleetctl upgrade-agent <机器> --yes` 重发令牌（中控用恢复的 SSH 密钥登录）；不确定就 `fleetctl upgrade-agent --all --yes`。
9. 新机器的 SSH 主机指纹变了（第 4 步没放回 sshd 主机密钥才会；放回了就和以前一致）：PVE 的拉取按 accept-new 只认第一次记下的指纹，会拒绝连接（`systemctl --failed` 里 fleet-backup-pull 失败）。在 PVE 上 `ssh-keygen -R <中控主机>`（拉取用的主机名或 IP），再手动跑一次 `systemctl start fleet-backup-pull` 记下新指纹。
10. 删掉 `/root/restore`（里面有密钥）。

## 11. 访问入口

只有一个入口：`https://fleet.kismet613.com`，人用面板、fleetctl、agent 回连与上架出口校验（`/echo`）都走它；Caddy（官方源，`install.sh` 负责安装与生成 Caddyfile）终止 TLS 并反代到本机 fleet-server。

2026-10-22 晚起前面加了两台德国边缘机：DE 9929（189.24.84.181）与 Zouter（78.31.249.198）用 HAProxy 把 80/443 四层原样转发到源站（185.13.159.131），带 PROXY v2 头。`fleet` 在 CF 是灰云 CNAME 到 AxisNow 托管的调度域 `9f5f5f43.alidns-3.com`：大陆走 9929、境外走 Zouter，互为备份（TTL 60 秒，拨测三次失败切换）。源站的 Caddy 要认这两台的 PROXY 头，否则经边缘来的连接握手全断（agent 上报失败、面板打不开）：
- 这段配置放在 `/etc/caddy/global.d/edge-proxy.caddy`（全局选项里的 `servers :443` / `servers :80`：`proxy_protocol` 只 allow 两台边缘、`fallback_policy reject`，不带头的直连照常；`protocols h1 h2` 关 h3，四层转发下 UDP 拿不到真实 IP），`http://` 跳转 HTTPS 放在 `/etc/caddy/sites.d/http-redirect.caddy`（自动生成的 :80 服务套不上 PROXY 包装，要显式建）。fleet.toml 要 `trust_forwarded_for = true`，`/echo` 与访问来源才是真实 IP。
- **不要直接改 `/etc/caddy/Caddyfile`**：每次部署由 install.sh 重写（旧文件留 `Caddyfile.bak-<时间>`），只 import 上面两个目录。本机再绑别的域名：站点块放进 `sites.d/<名字>.caddy`，`systemctl reload caddy`；DNS 同样灰云 CNAME 到调度域（根域名不行，CF 拉平会丢地理信息）。
- 边缘机换 IP：改 `global.d/edge-proxy.caddy` 里的两处 allow。
- **软路由接入预检**：接入脚本（一键部署的「上传密钥」、「在路由上执行命令」）先查路由有 OpenSSH 客户端、`/etc/dropbear`，以及 dropbear 在本机 22 端口监听（读 `/proc/net/tcp`、`tcp6`）：隧道固定转发到路由的 `127.0.0.1:22`，dropbear 改了端口或用 `Interface` 只绑 LAN 口时转进来的连接会被拒。不满足时报「路由的 SSH（dropbear）没在本机 22 端口监听」并附当前 Port / Interface，这一步就失败，一键部署写回原来的隧道密钥，在线的路由不受影响。
- **软路由隧道不走边缘机**：路由的 fleet-tunnel 连的是中控 sshd（`[routers] ssh_port`，默认 22），每次重连按主机名重新解析。回连主机是 `[routers] ssh_host`，没配时用 `public_url` 的主机名——也就是 `fleet` 域名，经边缘机只转发 80/443，路由断线后就回连不上（现在连着的隧道断开之后才受影响）。`ssh_host` 要配成源站 IP，或单独一个直指源站的灰云 A 记录；改了之后重启中控，给各路由重新生成接入命令或重新部署（init 脚本里写着旧主机名）。中控有软路由时启动和每 10 分钟自检一次，不对就开 `central_tunnel_host`（§12）。

2026-10-22 试过给人用入口挂 Cloudflare（普通橙云，以及「优选 IP + Worker」），实测后撤掉，只留直连：
- 大陆三网到源站的 TCP 延迟（itdog 全国约 290 节点）：电信 291 / 联通 273 / 移动 215 ms；CF 默认 anycast 234 / 300 / 192；优选 IP 能把电信或移动压到 80 ms 左右，但动态请求还要再走 CF → 法兰克福，日常（静态资源一年 immutable、首次之后只剩小接口）差别不大。
- 联通走 CF 免费版普遍更差：武汉联通实测所有 CF IP 都落美西，接口首字节 1.6–2.9 s、首屏 JS 一半超时；直连 1.2 s / 2.4 s。
- 同一个域名做不到「agent 直连、大陆走优选」：CF 的 DNS 不分线路，agent 经 Worker 会超免费额度（每天 10 万次）。真要三网最优，只能把 `fleet` 子域 NS 委派到支持运营商 / 境内外分线路的 DNS（华为云、DNSPod）。
- 不要把 `fleet.kismet613.com` 改成橙云：`/echo` 会拿到 CF 的 IP、上架出口校验全部失败，agent 的上报与长轮询还要过 CF 的机器人防护。

## 12. 中控自监控

中控自己出事（进程挂了、卡住、磁盘快满、备份停了、通知发不出去）也要有人知道。

**死人开关**（推荐配）：在 healthchecks.io（或自建的 Healthchecks 等收 ping 的服务）建一个检查，周期 1 分钟、宽限 5 分钟，告警发到不经过中控的地方（手机 App、邮件）；把它的 ping 地址写进中控 `/etc/fleet/fleet.toml`，`systemctl restart fleet-server` 生效：

```
[selfmon]
heartbeat_url = "https://hc-ping.com/<检查的 uuid>"
```

告警循环每轮（30 秒）评估成功后最多每分钟 GET 一次这个地址。中控进程挂了、卡住、连不上数据库导致评估一直失败、整台断网时 ping 就停了，由那边报警——这些情况下中控自己的通知渠道也发不出去。不写不发；ping 失败只在 `journalctl -u fleet-server` 里记一条 warn（地址里带着检查的密钥，不写进日志）。验证：重启 fleet-server 后一分钟内 healthchecks 的检查显示刚收到 ping。

**中控自身的告警**：规则 `central_` 开头，告警对象是「中控」（不是机器：告警页对象列写「中控」、点不开；`fleetctl --json incidents` 里 `subject_id` 为 null、`subject_name` 为「中控」），照常走通知渠道、告警页、`fleetctl incidents`。告警循环每轮评估完机器后检查，不去抖，恢复后再出现新开一条；被静默的不开、不发（只能「全部机器 + 规则」静默，如 `fleetctl silence add --all --rule central_backup_stale --for 24h --comment … --yes`）；严重的每 4 小时提醒一次。

- `central_channel_failing`（严重）：某个启用的通知渠道连续发送失败满 5 分钟，每个渠道一条，摘要写渠道名和最近一次失败的原因；这条发给其它渠道，不发给它自己。发往它的通知在库里排队重试，入队满 30 分钟还发不出的放弃（发送记录里一条失败）。改好配置后在网页「设置 → 通知渠道」点「测试」：测试发成功也算恢复，下一轮（≤30 秒）关掉，排着的通知随后补发。渠道停用、删除时这条告警直接关掉，不发恢复。
- `central_backup_stale`（警告）：`/var/backups/fleet` 里最新一份备份（`fleet-*.tar`、加密的 `fleet-*.tar.age`）超过 26 小时，或目录里一份都没有、读不了。每天 03:30 备份，没做成约两小时后报。`systemctl status fleet-backup`、`journalctl -u fleet-backup -n 20` 查原因，修好后 `systemctl start fleet-backup` 做一份，下一轮恢复。备份不在默认目录时在 `[selfmon]` 写 `backup_dir = "…"`；目录不存在（没装备份，如实验室）不检查。
- `central_disk_low`（严重）：中控本机 `/`、`/var/lib/postgresql`、`/var/lib/fleet`、备份目录所在的文件系统可用空间低于 10%（同 `df` 的 Avail 占 Size），回到 11% 以上恢复。写满了 PostgreSQL 会停、中控跟着停：`df -h`、`du -sh /var/lib/postgresql /var/backups/fleet /var/log/journal` 找大头（原始时序按 `[retention]` 只留几天，备份留最近 14 天每天最后一份、另加最新 3 份）。
- `central_ingress`（严重）：有自己 agent 的在用机器里同时离线的超过一半、且至少 3 台。中控和库都好着，是 agent 到不了中控：查边缘机反代、Caddy、域名解析（从别的机器 `curl -sI https://<中控域名>` 试）。期间不再按台开「agent 离线」；这条恢复后仍没回来的再按台报。
- `central_tunnel_host`（警告）：软路由隧道回连的主机（`[routers] ssh_host`，没配时 `public_url` 的主机名）不是中控：解析不了，或解析到的地址里没有中控本机网卡上的，也没有连它的 SSH 口拿到的主机公钥是中控 sshd 的（`[routers] sshd_host_key`；中控在 NAT 后时靠这一步认出自己），而且至少有一个地址连上了、公钥是别人的（多半是 CDN / 边缘机）。A 与 AAAA 并存时任一个地址对上就算中控；SSH 口连不上（超时、拒绝，可能只是中控连不回自己的公网地址）只算判断不了，不开告警、中控日志里写一行。摘要写解析到哪、哪个地址怎么不对。现有隧道断线后才会受影响：按 §11 把 `ssh_host` 配成源站 IP 或单独的灰云域名，重启中控后给路由重新接入 / 重新部署。只在有软路由时检查，启动时与每 10 分钟查一次，对了就恢复。
- `central_view_stuck`（严重）：机器视图（列表、总览、实时推送、告警评估共用的那一份）连续 2 分钟算不出来。视图查询每条 15 秒超时，重算一次最多 20 秒（排队等别人算完另算 20 秒），失败时先用上一份顶 1 分钟（这期间有过资源变更——改名、退役、改订阅等——就不顶，接口回 503 让页面重试，免得一直显示改动之前的），再久告警评估就跟着失败、死人开关停止 ping。多半是有查询被锁住（迁移、建分区排在父表锁后面）：`select pid, wait_event_type, state, now() - query_start, left(query, 80) from pg_stat_activity where datname = 'fleet' and state <> 'idle' order by 4 desc`，看是谁拿着锁。算成一次就恢复。

**后台任务监督**：中控里的后台循环（作业引擎、告警、实时指标、访问汇总、来源画像、通知发送、分区与保留期维护、小时汇总）panic 或意外退出时，`journalctl -u fleet-server` 记一条 error（「后台任务「…」…，10 秒后重启」），10 秒后原地重启，其余照常。作业引擎也一样（清旧租约只在中控启动时做一次，正在推进的作业不会被再领）。告警循环一直起不来时死人开关会报。

## 13. 访问记录保留期

访问监控照常记录（哪个节点、什么时候、从哪个来源 IP、访问了哪个域名 / IP），但访问记录只留一段时间，到期中控自动删除。两个天数，在网页「设置」里改，或 `fleetctl settings retention`（不带参数看现在的；`--raw N --hourly N --yes` 改，只给一个时另一个不变）；各 1–90 天，汇总不短于原始记录：

| 天数 | 默认 | 管什么 |
|---|---|---|
| 原始记录 `raw_days` | 7（没在面板里改过时取 `fleet.toml` 的 `[retention] access_days`） | 每一条访问记录（访问页「原始记录」、机器抽屉的最近记录）；agent 上报的更早的记录不再收 |
| 汇总 `hourly_days` | 31 | 小时汇总（访问页的概况、目标、来源、新目标，机器抽屉的访问与来源画像）、目标首次出现、来源 IP 画像缓存；访问页最长只能看这么久（30 天的窗口要汇总留 30 天以上） |
| 来源画像（只读） | 跟汇总一样，但不短于 IP 情报的学习期（7 天） | 每个节点见过哪些运营商 / 城市 / 接入方式 / 机房来源 IP，以及已恢复的画像异常告警 |

- **多久生效**：保存后立即在后台按新期限清一次，一般几秒，要删的多（比如汇总从 90 天改成 7 天）时几分钟；之后每小时按当前期限清一次。原始记录按天删整天的分区，最多多留不到一天；汇总按小时删。
- **调短会删数据**：超出新期限的访问记录、汇总与来源画像都删掉，找不回来；调长只影响之后的，已经删掉的不会回来。改动写审计（「操作记录」里「修改访问记录保留期 · 原始记录 7 → 3 天，汇总 31 天」），只读的 API 密钥改不了。
- **「新」的含义**：「新目标」「来源出现新运营商 / 新城市」「机房 / VPN 来源」都是「保留期内没见过」：一个值超过期限没再出现、记录删了，之后再出现就算新的（画像异常会再告警一次）。来源画像一直保留到学习期结束，学完不会因为学习期里见过的值被删掉而误报；一个节点闲置超过来源画像的保留期，画像全删光，之后再有流量学习期从头算。
- **备份**：每日备份（§10）不含原始记录，但含小时汇总和来源画像，删掉的这些在备份里留到备份轮换掉（中控 14 天、PVE 30 份）。要立刻不留，删掉旧备份。
- 直接改库里的 `app_setting` 要重启 fleet-server 才生效（进程里缓存了一份），请只用网页或 fleetctl 改。

其它几个保留期写在 `fleet.toml` 的 `[retention]`（不写照默认，改了重启 fleet-server 生效、下一次每小时的清理按新值删）：`raw_days`（原始时序：主机指标、入口流量、探测、软路由指标，默认 3）、`reach_days`（客户入口连通性原始记录，默认 2；小时汇总一直留着）、`ping_days` / `ping_hourly_days`（三网 PING 原始记录 / 小时汇总，默认 7 / 90）。

## 14. 用 agent 从中控全量运维

密钥都放在中控上：登录全部机器与软路由的 SSH 私钥、数据库与 `secret.key`，以及本机 fleetctl 用的全权 API 密钥 central-local。用户换哪台设备都只要能 ssh 进中控（root），在那里起 agent（Claude Code 等），就能做网页面板能做的一切，并直接登录任意机器 / 软路由；笔记本上不放任何令牌或机器密钥。

### 怎么开始

1. `ssh root@<中控>`（生产：本机别名 `debian13`，没配这个别名的机器上写地址 `185.13.159.131`）。
2. agent 两种跑法，令牌都不出中控：在中控的 `/root` 下起 agent（如 `claude`，Claude Code 要自己在中控上装好、登录）；或者 agent 留在手边的设备上，每条命令经 ssh 在中控上执行（`ssh debian13 'fleetctl --json status'`），这时先让它 `ssh debian13 cat /root/AGENTS.md` 读一遍中控上的说明。部署已经放好：
   - `/root/AGENTS.md` 与 `/root/CLAUDE.md`（同一份，模板 `deploy/central/central-agents.md`，每次部署覆盖）：这台机器是什么、规矩（改动前想清楚影响；删除、退役、全局维护、全部升级等先向用户确认）、常用命令、日志与备份在哪、出问题先看什么。
   - `/root/.claude/skills/fleet-ops/SKILL.md`：fleet-ops 技能（Claude Code 自动加载，别的 agent 按 AGENTS.md 的指引去读）；同目录的 `json-fields.md` 是 `--json` 字段速查（SKILL.md 里指明要解析字段时先读它）。
   - `/usr/local/bin/fleetctl` 与它的配置 `/root/.config/fleetctl/config.toml`（0600，地址是本机回环 + `fleet.toml` 的 listen 端口）。`fleetctl whoami` 应显示 `apikey:central-local` 与四个权限。
3. 登录机器：`fleetctl ssh 团队1-03`（交互式）、`fleetctl ssh 团队1-03 -- 'df -h'`（执行完退出，退出码同远端）；软路由 `fleetctl ssh router <名称>`。用中控的密钥、只认中控记下的主机指纹（机器 `/var/lib/fleet/known_hosts`；软路由 `/var/lib/fleet/router_known_hosts`，按别名 `router-<id>`，经它的反向隧道 `127.0.0.1:<隧道端口>`）；同机 IP 节点登录的是宿主机。只在中控上能用：读不到 `/etc/fleet/ssh/id_ed25519` 时报「先 ssh 进中控」。带命令时标准输入照样转给远端（同 ssh），在脚本循环里调用要加 `</dev/null`。

### central-local 密钥

- 由 `fleet-server local-admin -c /etc/fleet/fleet.toml` 建（只许 root），部署每次跑一次：配置里的令牌还对得上一把有效、权限齐全的 central-local 就不换（正在干活的 agent 不会因部署失效）；没有、配置丢了、在网页上被撤销、权限不全（以后加了新 scope）时新建，并撤销其它有效的 central-local。和别的密钥一样库里只存 sha256 与前缀，令牌只在那个 0600 的文件里，不打印。
- 轮换：`/opt/fleet/fleet-server local-admin -c /etc/fleet/fleet.toml --rotate`，旧的立即失效（连着的 `fleetctl watch` 马上断开），下一条 fleetctl 命令自动用新的。
- 在网页「设置 → API 密钥」撤销它同样立即生效；下次部署（或手动跑 local-admin）会建一把新的。名称 central-local 留给它，网页上建不了同名密钥。
- 从备份恢复后要跑一次 local-admin（§10 第 5 步）：恢复的库里是备份时的那把，对不上配置里的令牌。

### 审计里怎么区分是谁做的

操作记录（`fleetctl audit`、网页侧栏「操作记录」）的「操作者」：

- `apikey:central-local`：中控上的 fleetctl——用户 ssh 进中控后，agent 或人做的。
- 用户名（如 `kismet`）：在网页上登录的人。
- `apikey:<其它名称>`：别的 API 密钥（脚本、别处的 fleetctl）。
- `cli`：中控命令行（`user-set`、`user-del`、`totp-reset`，以及 local-admin 新建 / 撤销 central-local，摘要写「中控命令行 local-admin」）。
- `系统`：中控自己做的——备用团队的机器到期自动回收（审计 detail 与作业参数里 `auto` 为 `spare_expiry`，退役原因接上「备用到期自动回收（到期日 …）」）、已退役的机器收进回收站（`machine.recycle`，`auto` 为 `retired_sweep`）、回收站里的机器自动物理删除（`machine.purge`）、自动续费（`renewal`，备注「自动续费」），见 §2。

`fleetctl ssh` 每次登录记一条「SSH 登录」（`ssh.login`：对象、交互式还是带命令；命令内容不记）；要留命令全文的单条命令用 `fleetctl exec`。在中控上绕开 fleetctl 直接 ssh、psql 做的事不进审计。

### 为什么笔记本上不再需要令牌

- 令牌和机器密钥原本是让笔记本上的 fleetctl / agent 代表你去中控做事；现在 agent 直接跑在中控上，用本机的 central-local，令牌不出中控。
- 换设备只要能 ssh 进中控（把新设备的公钥加进中控 root 的 `authorized_keys`）；设备丢了，删掉它在中控上的公钥即可，不用逐个轮换 API 密钥。
- 笔记本上已有的 API 密钥用不着了：在网页「设置 → API 密钥」撤销，删掉本机的 fleetctl 配置与令牌文件。
- 代价是中控的 root 登录就是一切的钥匙（本来也是：中控上有全部机器的私钥与库）。中控的 sshd 只开公钥登录（`PasswordAuthentication no`），root 的 `authorized_keys` 只留在用的设备。怀疑中控 root 被别人用过：轮换 central-local 不够，中控上的 SSH 私钥、`secret.key`、库都当作泄露处理。

## 15. 网页终端

网页上机器的「终端」直接打开它的 root shell（常换设备也不用带密钥，登录密钥只在中控）：中控用自己的密钥和 known_hosts 登录，同远程执行（主机指纹不对就连不上，按 §4 处理），同机 IP 节点登录宿主机。只给登录用户（API 密钥、fleetctl 都不行）；每次打开前再输一次密码（开了两步验证是验证码），同一个登录会话 5 分钟内输过的免输。每人同时最多 3 个、全中控 8 个；15 分钟没有输入、连续开满 2 小时自动断开。不用配置；协议与限制见 API.md「网页终端」。

**审计在哪看**：网页「操作记录」（机器抽屉的最近操作）或 `fleetctl audit --target <机器>`，每个终端两条：「打开网页终端」（谁、哪台；同机 IP 节点写「登录宿主机 …」）与「关闭网页终端」（时长、上行 / 下行字节数、为什么断）；`fleetctl --json audit` 的 `detail` 里另有来源 IP、登录会话 id（同「设置 → 账户安全 → 登录会话」里的 id）、ssh 退出码。**终端里输入的命令不记**：要留痕的改动照旧用 `fleetctl exec`（命令全文进审计）。只有「打开」没有「关闭」的，是终端开着时中控异常退出了（崩溃、被强杀；正常重启会先断开终端、写完「关闭」）。

**踢掉一个终端**（比如别的设备上忘了关的）：
- 撤销开它的那个登录会话：网页「设置 → 账户安全 → 登录会话」里撤销（对上「打开网页终端」审计里的会话 id），它开的终端立刻断开，断开原因写「登录会话已失效」；这个会话没用掉的票据、5 分钟免输一并作废。怀疑密码泄露就改密码（其它设备全部退出，终端随之断开）。
- 在中控上以 root 结束那个 ssh：`pgrep -u fleet -af -- '-tt root@'` 列出网页终端的 ssh（fleet 用户起的；目标 IP 在命令行最后。root 自己 `fleetctl ssh` 起的不在里面），`kill <pid>`；终端随即断开（原因写 ssh 退出码 255），「关闭」审计照常写。
- 重启 fleet-server（含部署）会断开全部终端：收到退出信号后先以「中控正在重启」断开（浏览器看到原因、「关闭」审计写完，最多等 2 秒），重新起来之前开不了新的。

断开时中控结束本地的 ssh，远端的 shell 随连接断开收到 SIGHUP 退出；`nohup`、`setsid`、`systemd-run` 起的后台进程照常留着。

**日志级别**：生产不要把 `tungstenite` / `axum::extract::ws` 的日志级别调到 trace（`RUST_LOG`）：trace 会把帧内容写进日志，包括票据和键入的内容。

## 16. 汇率（计费统一按美元）

价格照供应商收的币种录入（套餐、订阅、续费记录，CloudSilk 这类收人民币的就记 CNY），网页与 fleetctl 展示的月费、合计一律折成美元：首页「每月费用」、机器卡片与表格的「$xx/月」（原价与汇率在悬停或副行）、费用页、团队与套餐页、`fleetctl status` / `billing` / `ls --due`。折算由中控按汇率算好（四舍五入到分，合计是逐台折好的相加），口径见 API.md「汇率」。

- **自动更新**：中控每天从 ECB 参考汇率（frankfurter，免费、不要密钥，中控要能出网到 `api.frankfurter.dev:443`）拉一次。失败保留上次的值，`journalctl -u fleet-server | grep 汇率` 看原因，一小时后自动再试；网页「设置 → 汇率」与 `fleetctl settings fx` 会显示最近一次失败。换汇率源或关掉自动更新在 `/etc/fleet/fleet.toml` 写（改完 `systemctl restart fleet-server`）：

```toml
[fx]
auto = true                                              # false = 只用手动设置的汇率
url = "https://api.frankfurter.dev/v1/latest?base=USD"   # 回包 {base:"USD", date, rates:{CNY:…}}（1 USD 合多少该币种）
```

- **手动设置**：网页「设置 → 汇率」或 `fleetctl settings fx <币种> --per-usd 7.12`。手动的优先，之后自动更新不改它（自动的值照样更新、表里看得到），要跟回市场价就「改回自动」（`--auto`）。改动写审计「修改汇率」。
- **没有汇率的币种**（源里没有、也没手动设）：费用不折算、不当 1:1，各处标「未折算」，首页合计单列、不算进总数。看到「在用但没有汇率」就手动设一个。
- 汇率存在 `app_setting` 的 `fx_rates`（JSON），随每日备份；不要直接改库（改坏了会当作没有汇率），用网页或 fleetctl。
- 续费记录（实付金额）、回收站里的价格是历史账目，照原币种显示，不折算。

## 17. 探测点（从靠近客户的地方测线路机入口）

中控在德国，客户在中国大陆：中控连得上线路机不代表客户连得上，偶尔连不上也不代表客户受影响。探测点是放在靠近客户的地方（家里 PVE 上的容器、阿里云香港）的一台小机器，跑 `fleet-agent probe`，每 30 秒连一遍各线路机的客户入口（同中控的轮换、对照目标与作废规则），另记建连延迟。设置里的「探测顺序」决定线路机卡片的心跳格、入口表的「连不上」、`relay_unreachable` 看哪一路：按顺序用第一个能用的探测点（第一个是主探测来源），都用不了时由中控代测（DESIGN.md「探测点」）。生产的顺序是 PVE → 香港 → 中控。

放在家里 / 办公室网络里时，探测点的出网必须是**直连**的宽带：网关上跑着 OpenClash 之类代理（旁路由）时，到线路机的连接会被代理接走，测到的是代理的结果。生产的 PVE 探测点是 PVE 上的容器 CT 180 `fleet-probe`（Debian 13，192.168.31.59，网关指向主路由 192.168.31.1、不经旁路由 192.168.31.2），宿主机自己的网关不动；建容器后先 `curl ip-api.com/line` 核对出口是本地宽带再装。

要求：x86_64 Linux（dist 里的 fleet-agent 是 musl 静态的，Alpine 直接跑），systemd 或 OpenRC，能出网访问中控（https）与对照目标（1.1.1.1 / 8.8.8.8 / 223.5.5.5 的 443，任一连上即可；大陆的网络连不上前两个，靠 223.5.5.5）；不需要公网入站，几 MB 内存。

**加一台**（二选一）：
- 中控能 SSH 到它（有公网 IP，NAT 后面但 22 映射出来了）：`fleetctl probe add 香港 --host <IP> [--ssh-port 22]`。中控用自己的密钥登录 root（主机指纹首次记录、之后严格校验），推 fleet-agent 到 `/opt/fleet/`、写 `/etc/fleet/probe.toml`（0600）、装服务，等到首次上报才算完。登不进时报错里有中控公钥全文：在探测点上把它加进 `/root/.ssh/authorized_keys` 再执行一次 `fleetctl probe install 香港 --host <IP>`。
- 不让中控 SSH：`fleetctl probe add 香港`（或网页 设置 → 探测点 → 新增）打印一条一次性安装命令（30 分钟内有效、只能用一次），在探测点上用 root 执行；它下载 fleet-agent、装服务，半分钟内 `fleetctl probe ls` 显示在线。过期了 `fleetctl probe install 香港` 重新生成。
- 装好之后放进探测顺序：`fleetctl probe order PVE 香港`（网页 设置 → 探测点 → 探测顺序，可以加入、移出、调先后）。中控自己的检查默认开着，顺序里的探测点都用不了时由它代测；不想要德国的结论可以 `fleetctl probe central off`（这时都用不了就标灰，线路机整台挂了仍有 agent 离线告警）。在顺序里的探测点不能停用、删除，先 `probe order` 把它移出去。

**服务**：OpenRC（Alpine）是 `/etc/init.d/fleet-probe`（`supervise-daemon` 守护、挂了 5 秒后拉起、开机启动），日志 `/var/log/fleet-probe.log`（只在出问题时写、同一个问题 10 分钟一条，不轮转也涨得很慢）；systemd 是 `fleet-probe.service`（`journalctl -u fleet-probe`）。以系统用户 `fleet-probe` 跑。

**它判不了的时候**：
- 每轮对照目标（1.1.1.1 / 8.8.8.8 / 223.5.5.5 的 443）都连不上：这一轮作废，只算心跳。在线、但 3 分钟里没有一轮被采纳（`fleetctl probe ls` 状态「在线（探测无效）」，网页「探测无效」并写原因）就当它离线：轮到顺序里的下一个（卡片写「香港探测点（代替探测无效的PVE探测点）」，都用不了时「中控（代替…）」），开 `probe_point_offline`。离线后刚回来的那一轮作废不算，从回来时算起。
- 对照目标通、三台以上线路机全部连不上：照记（以前整轮作废），`relay_unreachable` 摘要写「所有线路机同时连不上，可能是供应商整体故障」。这一路是探测点、顺序里的下一路（后面的探测点，没有就中控）最近 2 分钟连得上线路机时，摘要改写成「所有线路机同时连不上，但香港探测点连得上：多半是大陆方向到线路机被封，或 PVE探测点所在网络出境异常，先看客户软路由出口是否正常」（只改说法，照记照告警）；这一路若是代替离线主探测点的后面一路（如香港代测、再后面的中控连得上），只写「…但中控连得上：多半是香港探测点所在网络出境异常」，不提大陆方向。
- 「多久没上报」「多久没采纳」都扣掉中控收不到上报的时段（中控或库停一阵恢复后不会先判离线、退回中控再切回来，同 agent 离线）。

**长期数据**：网页 设置 → 探测点 的列表可以切 1 小时 / 24 小时 / 7 天 / 30 天看到各线路机的平均延迟与成功率；线路机抽屉「连接质量」的「客户入口连通性」里，中控与各探测点并排看近 24 小时 / 7 天 / 30 天。1 小时以内读原始记录（`relay_reach`，留 `[retention] reach_days`，默认 2 天），更长的读小时汇总（`relay_reach_hourly`，每 5 分钟随遥测小时汇总重算，一直留着；删探测点时它的一起删）。

**排障**：
- `probe_point_offline` / `fleetctl probe ls` 显示离线：在探测点上 `rc-service fleet-probe status`（或 `systemctl status fleet-probe`）、看日志。「连不上中控」查它的出网与 DNS；「中控说令牌无效」是探测点被删除或重装过（重装：`fleetctl probe install <名>`）；「这一轮作废：对照目标都连不上」是探测点自己的出网坏了（只算心跳，不判线路机）。
- 卡片上写「中控（代替离线的香港探测点）」：主来源离线，暂由中控代替——连不上照报，连得上不算恢复，等它回来再判。
- 升级：`fleetctl probe upgrade 香港`，探测点 30 秒内自己从中控下载 dist 里的 fleet-agent、核对 sha256、换上（旧的留成 `/opt/fleet/fleet-agent.prev`）、重启，命令等到它报上新版本。新版本 5 分钟内一次都没上报成功（起来了但连不上中控、一启动就崩溃被反复拉起）时自己换回 `.prev`、退出由服务管理器拉起旧版本，日志写「升级后 300 秒内一次都没能上报成功：已换回旧版本」；这个版本记在 `/opt/fleet/.fleet-agent.bad-sha256`，之后探测点不再换成它；新探测点每份上报都带上这个 sha256，中控看到要它升级到的正是这个，当场记成升级失败、不再下发；旧探测点不带，中控就在它下载过程序、5 分钟后还没报上新版本时记成升级失败、不再下发（旧版本不认 bad-sha256，不这样会反复换上、换回）。`fleetctl probe ls` 显示「升级到 X 失败，已回到 Y」：修好后发新版本（换掉中控 dist 里的 fleet-agent）再 `probe upgrade`；同一个版本再 `probe upgrade` 中控直接拒绝（409「这个版本在「X」上跑不起来过」），探测点也不会再换成它，除非重装探测点。试运行标记是 `/opt/fleet/.fleet-agent.trial`（读配置之前就看，新版本读不了配置这类启动就失败的也会换回；试运行期间不接受新的升级）；重装探测点会删掉这两个标记。
- 维护（探测点要停机、换机房）：`fleetctl silence add --probe 香港 --for 2h --maintenance --comment 换机房`，或网页 设置 → 探测点 那一行的扳手。期间 `probe_point_offline` 不开、开着的保持（不恢复、不发通知），列表显示「维护」；它仍是主来源时，离线照样退回中控代测（维护只管告警）。
- 删除：`fleetctl probe rm 香港 --yes`（主来源要先改走）；令牌立刻作废，它的静默一起删，探测点上的东西按打印出来的清理命令自己清。

## 18. 三网 PING（线路机往外测线路质量）

线路机每分钟往外连一轮目标（默认武汉电信 / 联通 / 移动的测速地址，TCP 80 口，每个 5 次），卡片上每个目标一行：当前延迟、左边延迟格、右边丢包格与当前丢包；抽屉「连接质量」里有延迟与丢包曲线。只展示，不开告警。它看的是线路好不好，客户连不连得上入口看探测点（§17）。

- 改全局目标：网页 设置 → 三网 PING，或 `fleetctl ping-targets set <槽位 1–8> --name 武汉电信 --target hb-ct-v4.ip.zstaticcdn.com`（`--target ""` 清空 = 不测）、`fleetctl ping-targets mode tcp|icmp`。保存后全部线路机代数 +1，一分钟内按新目标测。某台线路机正处在「重启 Xray 失败、暂停重试」时，改 PING 目标不会触发再次重启（新版 agent），但这台的新目标要等闸门期满、重试应用成功后才生效。
- 单台覆盖：抽屉「管理」→ 三网 PING，或 `fleetctl ping <线路机> set <槽位> --name … --target …`、`fleetctl ping <线路机> mode icmp|tcp|global`、`fleetctl ping <线路机> reset [<槽位>]`。看读数：`fleetctl ping <线路机>` 或 `fleetctl show <线路机>`。
- 要新版 agent：旧 agent 照常应用期望状态、只是不测（卡片上没有三网一块）。中控部署后升级线路机 agent（§7）。
- 某个目标一直 100% 丢包：先看是不是目标不开那个口（TCP 不写端口连 80）——换成 `host:443` 或改 ICMP 试；ICMP 时卡片悬停写的实际方式是 TCP，说明线路机上的系统 ping 用不了（没装 iputils-ping，或 agent 单元的 `CapabilityBoundingSet` 里没有 `CAP_NET_RAW`——旧单元缺它，`upgrade-agent` 补上；ping 走数据报套接字的系统还要 `sysctl net.ipv4.ping_group_range` 含 0），agent 日志里 10 分钟一条「ICMP 用不了」。

### 放置矩阵（节点放在哪台线路机）

线路机 agent 每 5 分钟对**全部**在用 VPS 节点（不含家宽代理、备用团队）各测一次到节点 IP 的往返：系统 ping 3 次（同三网 PING 的 ICMP），3 秒内有回应算通；系统 ping 用不了就不测。不连 SS 端口（节点防火墙只放行它所挂的线路机），也不连 SSH 端口（每 5 分钟几台线路机各握手一次，auth.log 一天多出近千行，fail2ban 开 aggressive 模式时会封线路机）。中控存小时汇总（`relay_node_rtt_hourly`，7 天）。

- 看：`fleetctl placement [--team …]` 或网页「线路」页顶部「节点放置」。最优 = 成功率 ≥ 99%、没故障、额度放得下（接下这个节点近 7 天的流量后，到重置日预计不超过上限的 80%，同一轮建议换过去的节点累计算）的线路机里往返中位数最小的；当前比最优慢 ≥ 10 ms，或当前成功率 < 99%，才建议换。节点有多条在用入口的，每条入口一行单条建议（`fleetctl move X --from A --to B`，`*` 标出它所在的各台线路机），不进批量命令；入口不是恰好一条在用的（还有待应用 / 停用的）只看、不建议。
- 某个节点在所有线路机上都「不通」：多半是节点或云厂商安全组挡了 ICMP（ufw 默认放行回显请求），不是链路坏；看 `fleetctl show <节点>` 的 TCP 探测。
- 要新版 agent：旧 agent 照常应用期望状态、只是不测（矩阵里那一列是「—」）。另外 2026-11-02 前装的 agent 单元缺 `CAP_NET_RAW`，系统 ping 报没权限，矩阵整片「—」：对线路机 `fleetctl upgrade-agent` 重写单元（生产先问用户），同上面三网 PING 一段。节点清单（上架、退役、换 IP）线路机每轮测之前向中控取一次（`GET /agent/v1/rtt`），不动期望状态、不动 Xray。

## 19. 软路由（采集、告警口径）
采集与接入的原理见 `routers/` 的模块注释，日常命令见 §2。这里是看告警、看状态时要知道的口径。
- **连不上 ≠ 采集出错**：隧道断了、ssh 自己失败（退出码 255）、隧道端口上读不到路由 SSH 的版本行，算连不上（`offline`，`router_offline` 严重）。连得上，但采集脚本出错、输出读不了、超时（这时隧道还通），算采集出错：状态照样 `online`、`error` 写原因、快照是上一次成功采集的，告警是 `router_collect_error`（「软路由读取出错」，警告、满 60 秒，摘要「连得上，但没读到状态：…」），其余几条保持原状。多半是路由固件 / ucode 不兼容或路由太忙，先看 `fleetctl router show`。
- **延迟测试单独一次执行**（每 5 分钟、45 秒时限，fleet 出口先测、没通的 fleet 出口当场重测）：没做成（超时、OpenClash 没在跑）只影响出口数据，出口沿用上一次、不算不通，原因在 `detail.openclash.delay_error`；这一轮也算测过，不会每轮重来。不通的 fleet 出口（连续两次不通）和刚测通一次、还要再确认的（`recovering`）不等 5 分钟，每轮采集（30 秒）单独重测（超过 5 个多半是路由自己的网络断了，不重测）；连续两次测通 `router_exits_down` 就恢复。
- **在线 / 离线即时**：中控每 2 秒看一眼本机隧道端口的监听（只读 `/proc/net/tcp`，不连路由），路由的隧道连上或断开时马上采这台一次，卡片随即变化；连上即恢复 `router_offline`。连不上满 3 分钟（180 秒，扣掉中控停机的时段）才开 `router_offline`，到点就评估、不等下一轮采集。路由断电、断网这类不告别的断开，中控 sshd 靠 `ClientAliveInterval 10` × 3 约 30 秒发现、放掉端口（`deploy/central/sshd-fleet-tunnel.conf`，部署时 `tunnel-setup.sh` 装上并 reload sshd，已连着的隧道不断：旧会话仍按旧配置运行，重连后才生效），路由重连时端口才腾得出来。
- **`router_exits_down` 只看 fleet 出口**（对上了 fleet 入口的）：客户自己的订阅 / 机场节点不通不报，「全部不通」升严重也只按 fleet 出口算，它们也不占重测名额。出口要从第一次不通的测试起连续不通满 180 秒才开（同机器 `egress_fail` 的 150 秒再多一轮 30 秒评估间隔，让机器告警先开、路由告警判 quiet 时看得到）。出口所指节点 / 线路机已有严重的机器告警（出口不通、TCP 不通、agent 离线；同机 IP 节点的 agent 离线由宿主机报，所以另看宿主机的 agent 离线；宿主机自己的出口 / TCP 告警不算，IP 节点有自己的 IP 和探测，各报各的）时，路由告警开着但不发通知（quiet：原因已经由机器告警在报）；机器告警先恢复、出口还不通时，路由告警等这台路由在 quiet 解除之后重新采集一次（快照的采集时间晚于解除的时刻；不按轮数等，补采几台、到点复查的评估也跑，快照可能还是旧的），出口还不通才补发「触发」，解除之后出口就好了的既不发触发也不发恢复；中控重启后从库里补回 quiet（还在告警、没通知过、没被静默的出口告警）。不通的出口指向的节点 / 线路机此刻在维护或告警中时摘要附上（「其中 2 个指向的团队2-03 正在维护」「1 个指向的线路机2 正在告警」），先去看那台；没有这类说明、且不通的出口全经同一台线路机时，摘要末尾写「（都经 线路机2）」（线路机在国内被挡时它自己的探测不一定看得出，线路机本身没告警，先去查它的入口）；不通的出口指向的都在维护中时不开（维护期间预期不通），开着的保持、不算恢复。
- **离线判断扣掉中控停机的时段**（同 agent 离线，§12 的上报中断补偿）：中控重启、库中断恢复后不会把一直在线的路由成批判离线。
- **重新接入**（重新生成接入命令、重新部署）：开着的 `router_offline` 直接关掉、不发「已恢复」（路由还没连上）；接入过的路由 30 分钟后还没连上，再开 `router_offline`（警告，摘要「重新接入后还没连上」）。生成接入命令时现在的隧道密钥照旧立即作废。重新部署在上传密钥、启动隧道这两步失败时，中控把原来的隧道密钥与端口写回，在线的路由不掉线（新私钥先写成 `id_ed25519.new`，启动隧道那一步才换上）。
- **配置读不了**：采集时 OpenClash 的配置取不回、解析不了，出口与 fleet 入口的对应沿用上次读到的（`config_stale`），不退化成「不是 fleet 的出口」；替换 / 换线路机执行时还读不了就失败（§6）。
- **时钟偏差** `clock_skew_s` = 中控时间 − 路由时间，正数是路由慢（同机器的 `clock_skew_ms`）；网页写「慢 3 秒」「快 2 秒」。
- **维护窗口**：客户现场计划断电、换宽带、换光猫前开（`fleetctl silence add --router <名称> --for 4h --maintenance --comment …`，或抽屉「管理 → 维护窗口」）。期间开着的告警保持（不恢复、不发通知）、不开新的，卡片显示「维护」、不描红；到期或提前结束（抽屉「结束维护」、`silence rm`）后按那时的状态再判。只想挡一条（如出口不通）用 `--rule router_exits_down`、不加 `--maintenance`。删路由时它的静默一起删。
- **资源阈值与机器不同**（CPU > 90% 持续 10 分钟，内存、存储 > 90%、连接表 > 80% 满 60 秒，合成一条 `router_resource_high`），原因见 DESIGN.md §6。
- **出口参数不一致 `router_exit_drift`**（警告）：出口对上了 fleet 入口、但 uuid / SNI / 公钥 / short-id / flow 和入口现在的不一样，或入口已删除 / 停用，持续两轮采集（满 30 秒）才开，替换、改出口指向的作业改配置的那一会儿不报；一致了满 60 秒恢复。入口还在用的一键同步（抽屉出口页「同步…」、告警页「同步出口参数…」、`fleetctl router sync`，作业 `router_sync`，同替换的改软路由出口：备份 → 改 → 重启 OpenClash → 测延迟，失败自动改回）；flow / 类型不对的同步改不了（脚本只换 server / port / uuid / SNI / 公钥 / short-id 六行），要在路由上改。
  - **只同步「已建立对应」的出口**：出口↔入口只按路由上报的 server:port 对应，路由上有人加一个指向别人入口（别的团队、备用团队、直出）的出口、凭据乱填，也会判成不一致；同步若照办，会把那个入口的真凭据写进这台路由。所以不点名（默认「同步全部」）只动「已建立对应」的：中控作业（替换 / 换线 / 改出口指向 / 同步）曾把这个出口写成指向该入口的，或这个出口在这台路由上曾经参数一致（表 `router_exit_link`，升级时按当时的快照回填：一致的，以及不一致但入口和路由同团队的）。其余的告警摘要写「从未对上过，未自动同步」、预览里列在「未自动同步」。确认是自己的：`fleetctl router sync <路由> --exit <出口>` 点名；点名的出口从没对上过、而且入口是直出 / 备用团队 / 别的团队的，被拒绝，要加 `--force`（网页上是勾选确认）。
- **临时切换**（`fleetctl router switch`、抽屉出口页「策略组 → 临时切换…」、告警页「临时切到…」）：只对 select 组，经 mihomo API 改当前选择，不改配置、不重启。可到时自动切回（后台任务每 30 秒看一次，不占采集循环，路由不在线就下一轮再试；到时原出口还不通、或它指向的节点有严重机器告警就不切回，推迟 1 小时再看，第一次推迟时通知渠道说一声）。没有规则用的组（如 mihomo 自带的 GLOBAL，抽屉里标「未被规则引用」）切了不影响流量，不给切换（API 409）；要把客户挪走用改出口指向。路由重启、OpenClash 重载（替换节点、改出口指向、同步出口都会重启它）后组回到默认选择，记录自动结束、待切回取消，审计「临时切换被路由改回」。OpenClash 开了「保存节点选择」的路由重启后可能还是切过去的那个出口，这时记录不结束、到时照样切回。
- **出口确认期间又不通**：不通的出口刚测通一次（还在确认）又不通，仍算连续不通（`fail_streak` 记 2），`router_exits_down` 不关、每轮照样重测；之前会当场关掉告警、发一次「已恢复」，等约 5 分钟一轮整测才再开。

## 20. 客户端订阅（自己的客户端按一个链接拉入口）
给自己的客户端用（Windows 上的 Clash Verge、家里 OpenClash 的 proxy-provider、v2rayN / Shadowrocket），代替「每次换节点、换线路机、轮换凭据后手写脚本重新生成节点列表再改两边配置」。
- 新建：`fleetctl sub add 家里`（`--protocols both` 同时出 AnyTLS，`--protocols anytls` 只出 AnyTLS，默认 `reality`；见 §21），或网页「设置 → 客户端订阅」。链接只显示这一次（库里只存哈希），丢了只能轮换。Clash Verge、OpenClash 用原链接（mihomo 的 `proxies:` 列表，可直接当 proxy-provider），v2rayN / Shadowrocket 在后面加 `?format=base64`。
- 规则（存团队 / 机器，不存入口参数，每次拉取按当时的在用入口现算）：默认全部团队、不含备用团队、含线路机直出。`--only-teams 团队1,团队2`（列了备用团队就带上备用）或 `--except-teams 团队3`；`--no-direct` 不带直出；`--include 备用-03` 另加某台（不看团队与直出），`--exclude 团队1-04` 一律不带（优先）。改规则 `fleetctl sub edit 家里 --exclude 团队1-04`（只改给了的，链接不变；`--include none` 清空）。
- 条目：只有在用的入口（节点、线路机也都在用；退役中、已退役、已回收的不算），健康与否都给（客户端自己测）。名字 `US · ATTVPS 家宽 · 团队1-06 · 203.0.113.5 · VLESS Reality`，直出 `US · GOMAMI 线路机1 直出 · 198.51.100.1 · VLESS Reality`（国家按机器的国家，没有的省掉；同一节点在几台线路机上都有入口时名字后括注线路机）。看现在的条目 `fleetctl sub show 家里`（不显示链接）。
- 换节点（replace）、换线路机（move / evacuate）、轮换入口凭据之后不用动客户端：下次更新订阅就是新的（Clash Verge 按响应头每 6 小时更新一次，也可以手动更新）。
- 停用 `fleetctl sub edit 家里 --disable`（拉取回 404，链接不变）；链接泄露了 `fleetctl sub rotate 家里 --yes`（旧链接立即失效，新链接只输出这一次）；删除 `fleetctl sub rm 家里 --yes`。`fleetctl sub ls` 看最近一次拉取的时间与来源 IP（10 分钟内只记一次；轮换后清空，看得出客户端换没换上新链接）。
- 安全：链接就是凭据，只给自己的设备。管理要 `secrets` 权限（同分享链接），新建、修改、轮换、删除记审计，拉取不记。拉取不经登录，错的令牌回 404 并计入登录失败限速（同一来源 15 分钟 20 次，和登录共用），响应 `Cache-Control: no-store`。

## 21. AnyTLS（线路机入口的第二种协议）
线路机的每个入口既能用 VLESS Reality，也能用 AnyTLS（同一份凭据）。官方 Xray 不支持 AnyTLS，线路机上另跑一个 sing-box 只做 AnyTLS 外壳：客户连 sing-box 的 AnyTLS 端口，sing-box 卸掉 AnyTLS 后经回环交给 Xray 上这个入口的桥接入站，访问策略、直出守卫、流量统计、访问监控、在线连接都还按入口算、和 Reality 合在一起。软路由（OpenClash）的配置不变，仍是 Reality。
- **端口**（入口端口 = P，默认端口池 20000–29999）：AnyTLS 公网端口 P + 20000（默认 40000–49999，sing-box 监听 0.0.0.0）、回环桥接端口 P + 30000（50000–59999，Xray 只听 127.0.0.1）；回环探测入站仍是 P + 10000。超出 65535 或和别的端口相撞的入口没有 AnyTLS（中控、agent 同一条规则）。调优档 tune-v3 把这两段也写进 `ip_local_reserved_ports`：已上架的线路机升级中控后要 `fleetctl tune <线路机> --yes`（或 `--all`），否则 sing-box 重启时端口可能被本机出站连接占去。
- **防火墙**：线路机上中控不管主机防火墙（入口端口一直是这样）；线路机或云厂商安全组若只放行了 20000–29999，要另放行 40000–49999/tcp。
- **程序与单元**：`lab/fetch-dist.sh` 把 sing-box（当前 1.14.4，musl 静态版；官方没有校验文件，sha256 按 GitHub 发布资产的 digest 写死在脚本里）下载到 dist，`deploy/central/deploy.sh` 有就随包带到中控 `/opt/fleet/dist/sing-box`。线路机上架、`fleetctl upgrade-agent` 时推到 `/usr/local/bin/sing-box`，装 `fleet-singbox.service`（动态用户、配置经标准输入、无特权，加固同 fleet-xray；单元变了只 daemon-reload，换了程序且在跑才重启一次——只断 AnyTLS 连接）。dist 里没有 sing-box 时只记警告，入口照常只有 Reality。
- **配置**：agent 全权生成 `/etc/fleet-singbox/config.json`（0600），每个有 AnyTLS 的入口一个 anytls 入站，密码 = 入口的 client_uuid（轮换凭据一起变）。自签证书 `/etc/fleet-singbox/cert.pem`、`key.pem`（0600）由 `sing-box generate tls-keypair <reality_sni> -m 120` 生成（10 年），reality_sni 变了重新生成；客户端一律跳过证书校验。配置变了才 `sing-box check` → 换上 → 重启 fleet-singbox：增删入口、轮换凭据会让这台线路机上**所有** AnyTLS 连接断一下（客户端自动重连），Reality 不受影响。没装 sing-box 时 agent 跳过、报「未安装」。
- **启用顺序**：部署中控（迁移 0094、期望状态格式 2）→ 中控 dist 里放好 sing-box → `fleetctl upgrade-agent <线路机>`（逐台；旧 agent 忽略 `anytls_port`，只有 Reality）→ `fleetctl tune <线路机> --yes` → `fleetctl show <线路机>` 的「AnyTLS」一行是「在跑」。
- **看状态**：`fleetctl show <线路机>` 的「AnyTLS」（在跑 / 没在跑 / 出错：原因 / 未安装 / 旧 agent 未知）；网页线路机抽屉「应用状态」、线路页卡片；日志 `fleetctl logs <线路机> --unit fleet-singbox`。出错常见原因：端口被占（看 `ss -ltnp | grep 4000`）、/etc/fleet-singbox 不可写（agent 单元是旧的：升级 agent）。
- **端口被占自愈**：AnyTLS 端口（默认 40000–49999）被本机出站连接（Xray 出站、agent 连中控的长连接）当本地端口占着时，sing-box 一个入站绑不上整个服务就退出。agent 每次启动 / 重启 fleet-singbox 前先 `systemctl reset-failed`（撞过 StartLimit 的单元停在 failed 会拒绝一切 restart），再用 `ss -K`（SOCK_DESTROY）关掉占着这些端口的非监听连接并在日志里写清条数和端口（TIME-WAIT 不算；端口上有别的程序在**监听**的不动，照常报错）；sing-box 没在跑（或要监听的端口没都听上）时 agent 每分钟左右再应用一次，不等配置变化。调优档保留段（tune-v3 的 `20000-59999`）只管以后新建的连接，已建立的老连接靠这条自愈，不用手动重启 Xray / agent。需要 agent 单元有 `CAP_NET_ADMIN` 和内核 `CONFIG_INET_DIAG_DESTROY`：2026-11-03 前装的单元没有前者，`fleetctl upgrade-agent` 重写单元（缺它时日志写「没关掉」，其余照旧）。AnyTLS 状态以当前实际为准（单元 active 且端口都在听 = 在跑），启动类的旧错误恢复后自动清掉。
- **给客户端**：`fleetctl share <入口>` 第二行是 `anytls://…?sni=…&insecure=1`；订阅 `--protocols both|anytls`（Clash 里是 `type: anytls`，`skip-cert-verify: true`）。只有线路机报了 sing-box 在跑时才给 AnyTLS（没在跑时链接是坏的），sing-box 停了订阅里的 AnyTLS 条目随之消失。
- **访问监控**：经 AnyTLS 进来的访问照常记到入口，来源 IP 为空（sing-box 从回环转进来，看不到真实来源）。
- **穿透入口**也有 AnyTLS：经 AnyTLS 进来的连接同样走隧道（`rvs-<入口>`），隧道断了 AnyTLS 和 Reality 一起不通。
- **按线路机选入口协议**：`fleetctl relay-set <线路机> --protocols anytls|reality|both`（网页线路机抽屉「应用状态 → 入口协议」）。`anytls` = 只留 AnyTLS：Reality 入站改听回环（公网连不上，正在用 Reality 的客户端断开），分享链接、订阅只给 AnyTLS，客户入口探测改连 AnyTLS 端口；要线路机 AnyTLS 在跑且 agent 是新版（否则先 `fleetctl upgrade-agent`）、这台上没有穿透入口、没有软路由出口指着它的入口（软路由只用 Reality），不满足时中控拒绝并写明是哪些。反过来，只 AnyTLS 的线路机上新入口自动按普通模式建，软路由出口也不能换到它上面（改出口指向、换线路机会被拒）。`reality` = 不提供 AnyTLS。`both` 是默认。改完代数 +1，线路机热更新，不重启 Xray；`fleetctl show <线路机>` 的「入口协议」一行看现在是哪种。

## 22. 计费台账（按节点数向团队收费）
- 口径：团队里在用、不在备用团队、没标不计费的 VPS / 家宽代理（含同机 IP 节点）每个是一个计费节点（名额）。**每个节点从自己的开始收费日起每满一个月收一次（一期，月底对齐）**，每一期只记「已收 / 没收」（默认没收，手动标）；按月看 = 每个节点起点在这个月的那一期。中控每分钟对账：节点离开 → 等补位，节点加入 → 待定；**24 小时内一进一出算替换**（新节点接过位置、开始收费日与收费状态不变），超过 24 小时没配上才算新增（开始收费日 = 加入那天）或减少（离开前已经开始的那一期照收，之后不收）。
- 首次上线：`fleetctl billing init --since 2026-10-01` 预览、加 `--yes` 执行；初始化之前对账不动（不会把现有节点当成新加入的）。之后个别开始收费日不对的用 `fleetctl billing slot <节点> --start <日期>` 改（改了以后期的起点变，原来标的已收要重新标）；系统外的节点用 `billing add`，不收钱的节点 `billing exempt <节点> --on`。
- 收钱：`fleetctl billing month <团队> [YYYY-MM]` 看这个月谁没收；收到了 `fleetctl billing paid <团队> <节点…> [--month YYYY-MM] --yes`（`--all` = 这个月所有没收的，`--unpaid` 改回没收；不加 `--yes` 只预览；节点名重名时报错并列出名额 id，改写 id 前缀）。网页「团队与套餐 → 计费台账」同一份：按月翻，每行「标记已收」。看增减：`fleetctl batch list <团队> --events`。
