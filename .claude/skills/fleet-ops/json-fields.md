# fleet-ops：--json 字段速查

要解析 `fleetctl --json` 的输出字段时先读这一份（SKILL.md 里只讲命令与规矩）。

- `ls`（每台一个精简对象）：`id name kind(relay|vps|proxy) lifecycle(active|provisioning|retiring|retired|failed) health(ok|degraded|down|unknown|maintenance|inactive) ip agent_online cpu_pct mem_pct disk_pct entries(入口数) open_incidents active_job{id,kind,state}`；百分比是整数，取不到为 null；家宽代理没有 agent，`agent_online` 为 null。`--due N` 时每项另有 `due_date due_days auto_renew`（`due_days` 按机器的账单时区算，负数是已过期几天）与 `fee{monthly_cents currency monthly_usd_cents usd_per_unit}`（月费的原币种与折成的 USD，没有汇率时 USD 两项为 null；没有订阅时 `fee` 为 null），表格多一列「月费」（USD，括注原价）。
- `show`（MachineView）：上面这些的完整版（`health.status`、`agent.online`、`host.{cpu_pct,mem_used,mem_total,disk_used,disk_total,load1}`、`entries[]` 完整入口视图），另有 `ssh_port revision`、`health.reasons[{key,rule_name,severity,text}]`（`rule_name` 是规则中文名，同通知）、`agent.health`（agent 自报：离线队列、访问日志解析不了 / 丢弃的行数等）、`failed_job`、`no_router_exits`（true = 团队里在用的节点、团队的软路由都看得清出口，却没有一个出口指着它：多半是出口改指向别处后留下的，看着在用其实没客户；文字输出「软路由」一行。用户问哪些机器没人用时据此回答，退役前仍先问）。
  `egress_ip`：端口转发型 NAT 节点的出口 IP（`ip` 是线路机连的入口），null = 出口就是 `ip`。
  同机关系：`host_machine{id,name}` 非 null 的是同机 IP 节点（它的 `agent`、`host` 都是宿主机的，agent 离线 / 高负载告警在宿主机名下；`logs --unit ssserver` 看它自己的实例 `fleet-ssserver@<端口>`，`exec` 在宿主机上执行；不能单独 `upgrade-agent`）；`ip_nodes[{id,name}]` 是宿主机上未退役的同机 IP 节点。
- `entries`（每个入口一个精简对象）：`id relay port node lifecycle(active|pending|disabled|removing|removed) applied apply_error mode(normal|reverse) tcp_ok egress_ok today_down today_up`（今日业务流量，字节）；`tcp_ok` / `egress_ok` 为 null 表示还没探测过。`node` 是「线路机名-直出」的是线路机直出入口：没有节点，`tcp_ok` 恒为 null；它出口不通时告警对象是线路机（`egress_fail`）；搬空不搬它，退役线路机时自动摘除。
- `incidents`（每条一个精简对象，`status` 里的 `incidents` 相同；`status` 的表格只列前 20 条——严重的在前、同级新的在前，末尾「另有 N 条」，要全部看 `incidents` 或 `status --json`）：`id severity(warning|critical) rule rule_name subject_id subject_name summary reopen_count recent_count chronic state(firing|resolved) opened_at resolved_at ack_by suggested`（`recent_count`：同一对象同一规则近 7 天开过几次（含这条）；`chronic`：它 ≥3，是老毛病；`suggested`：中控按规则给的、可以直接执行的 fleetctl 命令，只有进行中的这几条有，其余为 `[]`：egress_fail / router_exits_down → `router switch … --for 4h`（把选着坏出口的 select 组切到组里能用的出口）、router_exit_drift → `router sync`、线路机的 traffic_quota_high → `rebalance`、agent_offline → `logs`、nonbusiness_traffic_high → `logs` 与 `exec … 'ss -s; nft list ruleset | head -50'`、business_traffic_spike → 有 select 组用着它时 `router switch … --for 4h`，否则 `traffic --node <节点> --days 7`；VPS 节点的 tcp_fail / egress_fail 在 `chronic` 时另有 `placement --node <节点>`（已恢复的反复告警也有）；会改东西的照样先告诉用户；`ack_by` 非 null 即已确认；恢复后 30 分钟内复发会重开同一条并 +1，表格里显示「反复 N 次」；大于 0 说明在抖，查探测/网络而不是只看当前状态。机器、软路由、探测点、中控的告警都这样；严重度升级时确认会被清掉）。规则 key：agent_offline、clock_skew、no_entry、egress_fail、tcp_fail、renewal_due（过期后升为 critical；备用团队的机器只在还有软路由出口指向它时才报；旧记录里还有 renewal_overdue）、traffic_quota_high（流量额度：本周期已用 ≥ 90% warning、≥ 100% critical，不改健康状态，新周期或调高上限后自动恢复）、nonbusiness_traffic_high（非业务流量偏高：VPS 节点连续 2 个完整小时网卡超过业务的 4 倍、多出 > 2 GB，正常约 2.4 倍；有不经过入口的流量——被扫描、灌包或被滥用，也算额度。按 suggested 先 `logs`、再 `exec <节点> -- 'ss -s; nft list ruleset | head -50'` 看连接与防火墙，把看到的告诉用户，改密码、封端口、重装都先问；连续 2 小时正常自动恢复）、business_traffic_spike（业务流量突增：最近一个完整小时超过近 7 天同一小时中位数的 5 倍且 > 5 GB，数据不满 3 天不判；先 `traffic --node <节点> --days 7` 与 `access sources --node <节点> --window 24h`、`access targets --node <节点> --window 24h` 看是谁在用、用在哪，告诉用户；要保住别的客户才按 suggested 临时切走，先确认；连续 2 小时回到 2 倍以下自动恢复；这两条都不改健康状态，被打时 agent 常断线、读数上不去，报的是 egress_fail）、relay_apply_lag、relay_apply_error、relay_xray_down、relay_unreachable（主探测来源——中控或探测点——连续 3 轮连不上线路机的客户入口，或同一个入口端口最近 3 次都连不上，健康状态就变故障，告警再持续 1 分钟才开（整台不通约 5 轮、2.5 分钟），critical，摘要「…连续 3 次以上连不上客户入口」，开头写是谁测的、括号里有端口与原因）、host_cpu_high、host_mem_high、host_disk_high、ipintel_new_isp（来源出现新运营商）、ipintel_new_city（来源出现新城市）、ipintel_datacenter_source（机房 / VPN 来源 IP），这三个是 warning、学习期 7 天后才有；最后一次出现 24 小时后自动恢复，一直在出现的从首次出现起满 2 天也自动恢复（视为新常态，例如团队换了宽带，之后同值不再告警），都不发恢复通知，不用手动处理。中控自身的告警（对象是「中控」：`subject_id` 为 null、`subject_name` 为「中控」，不能 `show`）：central_channel_failing（通知渠道连续发送失败满 5 分钟，critical，摘要里有渠道名与原因；请用户在网页「设置 → 通知渠道」改配置并点「测试」，测试成功即恢复）、central_backup_stale（中控每日备份超过 26 小时没有新的，warning；`fleetctl server-logs` 帮不上，需要用户在中控上 `systemctl status fleet-backup`）、central_disk_low（中控本机磁盘可用低于 10%，critical，写满了中控会停；告诉用户尽快清理）、central_ingress（有 agent 的机器过半且至少 3 台同时失联，critical：边缘机 / Caddy / DNS 出问题，agent 到不了中控；期间不按台开 agent_offline）、central_view_stuck（机器视图——列表、总览、实时推送、告警评估共用的那份——连续 2 分钟算不出来，critical：期间机器告警停止评估、列表可能停在旧数据或报 503，`fleetctl status` / `ls` 也可能失败；多半是数据库有锁排队或慢查询，转告用户在中控上查数据库的锁与慢查询（`docs/OPS.md` §12 有查询语句），算成一次就自动恢复；AI 不要去 `show` 机器或逐台排查）、central_tunnel_host（「软路由回连地址不是中控」，warning：软路由隧道回连的主机——`[routers] ssh_host`，没配时 public_url 的主机名——解析到的不是中控（经 CDN / 只转发 80/443 的边缘机，或解析不了），摘要写解析到哪；现在连着的隧道不受影响，路由断线后就回连不上。转告用户把 fleet.toml 的 `[routers] ssh_host` 配成中控源站 IP 或一个直指源站的灰云域名，重启中控后给各路由重新生成接入命令或重新部署（`docs/OPS.md` §11）；AI 不要去改配置、不要去动路由）。这几条都要转告用户，AI 处理不了。探测点离线是 `probe_point_offline`（见「探测点」一节，`subject_name` 是探测点名，不能 `show`）。软路由的告警是 `router_` 开头的七条（见 SKILL.md 的「软路由」一节），`subject_id` 是路由 id、`subject_name` 是路由名，用 `router show` 看，不要 `show`。
- `silence ls`（每条一个精简对象；`silence add` / `silence rm` 输出新建 / 删掉的那一条，同形）：`id subject_kind(machine|router|probe_point) subject_id subject_name rule rule_name starts_at ends_at state(active|scheduled) is_maintenance comment`；`subject_kind` / `subject_id` 为 null = 全部（机器、软路由、探测点），`rule` 为 null = 全部规则；`state` 是 `active`（进行中）或 `scheduled`（已预约，还没开始）。只列没结束的。
- `billing`：`id name host_machine spare subscription sub_template traffic_limit_gb quota{limit_gb,limit_source,used,period_start,period_end,mode,counted_from,rule,base,base_at} quota_pct renewals renewal_count`。`subscription` 为 null 是没有订阅，否则 `{price_cents currency cycle(monthly|quarterly|semiannual|yearly) due_date due_days due_state(ok|soon|overdue) billing_tz auto_renew remind_days traffic_gb traffic_reset_day overrides monthly_cents next_due period_days}`，全是生效值（`due_state` 同续费告警：soon = 提前提醒天数内且不是自动续费；`next_due` = 推一个周期后的到期日，`renew` 不带 `--to` 时由中控算），`overrides` 是单独设置了的字段名（其余跟随 `sub_template`：`{price_cents currency cycle billing_tz remind_days traffic_gb traffic_reset(month|billing|rolling30)}`；`rolling30` 时跟随的 `traffic_reset_day` 为 null）；金额都是分（`price_cents` 3946 = 39.46，币种看 `currency`）。`traffic_gb` 0 / null = 不限，`traffic_limit_gb`（= `quota.limit_gb`）是生效的上限（null = 不限），`quota.limit_source` 是它的来源（`subscription` 单独设置 / `plan` 跟随套餐 / `host` 同机 IP 节点与宿主机共用 / `none`），`quota_pct` 是本周期已用（`quota.used`，字节）占它（GB × 10⁹）的百分比（向下取整，没有上限为 null）；`quota.rule` 是网卡计量规则（`min|max|sum|out`，null = 业务流量，下载加上传）；`quota.mode` 是 `monthly`（`period_end` = 下次重置日）或 `rolling30`（近 30 天，`period_end` 为 null）；`quota.counted_from` 非 null = 周期中途上架、这之前的用量不在 `used` 里；`quota.base_at` 非 null 是割接时录的接入前读数（`base`，字节，只读，下个周期自动失效）。本月网卡流量在 `show --json` 的 `nic{today_rx,today_tx,month_rx,month_tx}`（rx 下行、tx 上行；家宽代理、同机 IP 节点为 null），`month_counted_from` 非 null = 本月中途上架，`agent.nic_ifaces` 是计量的网卡。`renewals` 是最近 10 条续费记录（新→旧）`{id old_due new_due amount_cents note actor created_at}`，`renewal_count` 是总条数。
  计费统一按 USD：`subscription` 里另有 `monthly_usd_cents`（月费折成 USD 的分）、`price_usd_cents`（每期价格折成 USD）、`usd_per_unit`（所用汇率，1 单位合多少 USD；USD 为 1），由中控按汇率算好（`round(原币种分 × usd_per_unit)`，四舍五入到分）；三个都是 null = 没有这个币种的汇率、未折算（不是 0 元，也不是 1:1）。原字段 `price_cents` / `currency` / `monthly_cents` 照旧是供应商收的原币种。文字输出的「费用」行后面写「；折合 37.50 USD/月（1 CNY = 0.125 USD）」或「未折算」。
- `renew`：刚登记的这条续费记录（同 `billing` 的 `renewals[]`）。`subscription set`：改完的 `subscription`（同上，`due_days` 按新到期日算）；没有变化时不提交，输出现在的。
- `settings retention`（改了之后输出改完的，同形）：`{raw_days, hourly_days, min, max, profile_days}`；`raw_days` 是原始访问记录（每一条：时间、来源 IP、目标）留几天，`hourly_days` 是汇总（小时汇总、新目标、来源画像）留几天、也是访问页能看的最长范围，`profile_days` 是来源画像实际留几天（不短于 IP 情报的学习期，只读）。没有变化时不提交，输出现在的。
- `policy ls`：`draft_count teams[{id name mode domains draft revision nodes[{id name mode domains source(node|team|default) draft revision}]}]`；`domains` 是域名个数，`draft` 为 null 或 `{mode,domains}`；节点的 `mode` / `domains` / `source` 是生效值，`draft` / `revision` 是节点自己的。
- `status --json` 的 `overview.failed`：上架失败（lifecycle=failed）的机器数，算在「有问题」里。`show` 的 `failed_job{id,kind,state}`：上架失败或退役失败（退役中）的机器带最近失败的作业，拿它的 id 去 `fleetctl job` / `fleetctl retry`（`ls --status failed` / `ls --status retiring` 找出这些机器）。
- 不加 `--json` 的 `status` / `show` / `entries` / `incidents` 是给人看的：种类、生命周期、健康、严重度、规则、入口状态、作业种类与状态都显示中文；中文名和计费周期都取中控的 `/meta`（网页同一份）；所有命令表格里的时间都是组织时区（中控 fleet.toml 的 `org_timezone`，默认北京时间；`--json` 里是 API 原样的 RFC 3339）；`ls` 的种类 / 生命周期 / 健康列保留原值（就是 `--kind`、`--status` 的取值）。脚本和 AI 只解析 `--json`。
- `status --json` 的 `overview.monthly_usd`：`{cents, by_currency:[{currency,cents,usd_cents,usd_per_unit}], unconverted:[{currency,cents}]}`——每月费用折成 USD 的合计（分，逐台折算后相加）、各原币种的金额与所用汇率；没有汇率的币种不算进 `cents`，单列在 `unconverted`。`overview.paid_machines`：这个合计里算了几台（在用、不是闲置备用、有订阅的；文字输出「每月费用 … （在用 N 台）」读它，旧中控没有）。文字输出「每月费用」写 USD 合计，括注非 USD 币种的原价与汇率。
- `settings fx`：`{base, auto, url, fetched_at, rates_date, last_attempt_at, last_error, missing:[在用但没有汇率的币种], rates:[{currency, usd_per_unit, per_usd, source(base|manual|auto|null), auto_per_usd, manual{usd_per_unit,by,at}, in_use}]}`；`source` 为 null = 没有汇率（费用未折算）。文字输出只列在用和手动设过的币种。
- `status --json` 的 `overview.online` / `offline`：按 agent 连通计（家宽代理没有 agent 算在线），与健康无关。
- `status --json` 的 `overview.spare`：闲置备用（备用团队里没有软路由出口指向的在用机器，等到期放生）的台数。它们不计入 `nodes` 的 total 与各健康计数、也不计入 online / offline，不开告警（已开的悄悄关掉）；卡片上的健康状态照常显示。它们自己的健康计数在 `overview.spare_health`（同 `nodes` 的形状：`total ok degraded down unknown maintenance`），文字输出节点那行末尾「闲置备用 7（正常 3 · 故障 4；能顶替 3 台）」（能顶替 = 总数 − 故障 − 未知）。用户要找备用机顶替时先看这个，再 `fleetctl ls --team 备用 --status ok` 挑；`replace` 预览会提醒新节点故障 / 降级、快到期。`overview.monthly_usd`（每月费用）不含闲置备用（不续费；还被出口指着、有在用 IP 节点的备用机照常续费，算在合计里），闲置备用的月费在 `overview.monthly_usd_spare`（同形状加 `count`），`status` 文字在每月费用后附「另有闲置备用 N 台 …」。
- `status --json` 的 `overview.traffic_month`：`{up, down, counted_from}`——本月全部入口业务流量合计；`counted_from`（RFC 3339 或 null）非 null 表示在用线路机本月才接入、之前的量不在内，`status` 文字写「（10-22 起）」。
- `job`：`state`（queued|running|waiting|cancelling|succeeded|failed|cancelled）、`error`、`steps[]`、`logs[]`。`kind` 里 `provision_ip` 是上架同机 IP 节点，`reverse` 是穿透开关（步骤 `bridge_up` 推 bridge、`switch` 切换并验收、`bridge_down` 收起 bridge；`switch` 失败时中控已自动切回原模式，错误里写明）。
- `retire --json`：进备用 `{mode:"spare", name（备用里的名字）, from, recycle_on, ip_nodes:[{id,name,from}]}`；`--now` 为 `{mode:"now", job_id, ip_node_jobs:[{machine_id,name,job_id}]}`，后者是一并回收的同机 IP 节点各自的退役作业。不加 `--yes` 时 stdout 是预览：GET 预览原样 `{name, renames, ip_nodes, spare, routers, blockers, warnings}`（`move` 单个 `{ok, blockers, old_entry, routers, warnings}`，批量 `move` 与 `evacuate` 是 `{jobs[], router_restarts, warnings, …}`，各带 `ok` / `blockers` / `skipped` / `offline_routers` 中适用的），确认错误（`confirm_required`）在 stderr。
- `recycle ls --json`：`{items:[{id source(fleet|legacy) source_id machine_id kind name last_name team ip host_name provider plan service_ref price_cents currency cycle activated_at retired_at due_date recycled_at reason traffic_up traffic_down nic_rx nic_tx actor}], total, next_offset}`；`recycle show --json` 另有 `snapshot`。`recycle import --json`：`{dry_run, inserted:[{source_id,name,id}], skipped:[{source_id,name,why}]}`。
- `upgrade-agent --all --json`：`{jobs:[{machine_id,name,kind,job_id,after}], skipped:[{machine_id,name,reason}], order}`；`jobs` 按执行顺序，第一个是金丝雀，`after` 是它要等的作业（等的那个换上新版本后失败、或被取消，它就被取消）；`order` 是顺序说明，原样转述给用户。中控上没有 agent 程序时报错（409），不建作业。
- `tune --json`：`{jobs:[{machine_id,name,job_id}], skipped:[{machine_id,name,reason}]}`（`--team` / `--all` 时金丝雀失败则多一个 `stopped:true`，其余没提交）；逐键结果（`applied ok kept skipped[{key,why,got}] before{键:改前的值} params snapshot warnings[第三方调优残留] route{initcwnd,initrwnd} journald ntp nofile container`；撤销时 `rollback:true`）在作业 `job <id>` 的 `steps[0].output`。`ls` 每台带 `tune`、`show` 带 `tune`：`{profile,at,current,params}`（`current:false` 且 `profile` 为 null = 未调优或已撤销，非 null = 旧档；`params` = `{bw,bw_plan,bw_source,rtt,rtt_source,rtt_samples,mem_mb,buf_max}`，旧档 / 未调优为 null），家宽代理和同机 IP 节点为 null。
- `speedtest --json`：提交时是 `{machine_id,name,job_id,size_mb,target,target_name,traffic_mb}`；`--follow --json` 先输出日志行，最后一行 `{job:{…, steps:[{key:"speedtest", output:{target, target_name, url, size_mb, bytes, complete, avg_mbps, avg_mb_s, total_s, ttfb_s, remote_ip}}]}}`，`complete=false` 是时限内没下完（速率按已下载的算）
- `report uptime --json`：`{month, days, from, to, tz, items:[{id name team{id,name} provider{id,name} egress_total egress_ok egress_pct tcp_total tcp_ok tcp_pct outages longest_outage_min incidents}], providers:[{id name nodes with_data avg_egress_pct worst_egress_pct worst{id,name} avg_tcp_pct worst_tcp_pct outages incidents}]}`（`*_pct` 为 0–100，null = 没有探测；`longest_outage_min` 单位分钟，按失败次数估算）；`report monthly --json`：`{month, from, to, tz, traffic{down,up,total}, monthly_usd, machines, costly[], worst_uptime[], top_rules[], due_soon, overdue, text}`；`report monthly --send --json`：`{month, channels, text}`
- `exec`：`exit_code stdout stderr duration_ms truncated timed_out`；多台时是这些字段加 `machine` 的数组，某台没执行成（请求被拒、连不上）时那一项是 `{machine,id,exit_code:null,error:{code,message,status}}`。
- `ssh`：没有 JSON 输出（终端交给 ssh，输出是远端的原样），退出码同远端；登录之前的错误（找不到机器、不在中控上、审计没记上）照常是 stderr 的错误 JSON、退出码 1。

- `routers`：API 的 data 原样，每台 `{id name team{id,name} note tunnel_port created_at state(pending|online|offline) last_seen_at error summary deploy bootstrap_expires_at}`；`summary`（从没采集成功过为 null）：`uptime_s cpu_pct load1 cores mem_used mem_total disk_used disk_total conntrack conntrack_max temp_c wan{up,ip,rx_bps,tx_bps} openclash{enabled,running,version,mode,conns,up_bps,down_bps} exits{total,alive,dead,managed,drift,fleet{total,alive,dead},other} clients`（速率 bit/s，字节为单位的是内存、存储）。`exits.total/alive/dead` 是全部出口（含客户自己加的），`exits.fleet{total,alive,dead}` 只数 fleet 出口（对上了面板入口的，卡片、告警、文字输出都按它算），`exits.other` 是客户自己加的出口个数（不通不归我们管，单列、不算降级）；旧中控没有 `fleet` / `other`。路由离线（`state` 为 `offline`）时 `summary` 是掉线前最后一次读到的，`--json` 的每台都带布尔 `stale`（离线时为 true；`router show --json` 同）——不要把它当现状，文字输出里这些读数显示 `-`。
- `router show`：上面这些加 `switches[{group from to back_at by switched_at defer_why deferred_at}]`（进行中的临时切换，`from` 是第一次切之前的；`defer_why` 非空 = 到时原出口还没恢复、推迟了，`back_at` 是下次检查）与 `detail{system interfaces[] openclash exits[] groups[] clients[] collected_at}`；`groups[]` 每个 `{name type now all[] used}`（`type` 是 mihomo 的类型，`Selector` = select 组、能 `router switch`；`now` 当前选中的；`used === false` = 没有规则用它，切了不影响流量，`router switch` 会被拒，要挪客户用 `repoint`；缺省 = 不知道）；`exits[]` 每个 `{name type server port entry{id,name,node_id,relay_id,node_name,relay_name,port,lifecycle}|null sync(ok|drift|unmanaged) alive delay_ms delay_at fail_streak conns up_bps down_bps clients}`（`entry.name` 形如「团队2-03 · 线路机2:20003」；各出口的速率是按连接估的）；`clients[]` 每个 `{ip mac hostname online conns exits[{name,conns}]}`。`router add` 不带 --host 输出 `{id, bootstrap{cmd, expires_at}}`。
- `router changes`：API 的 data 原样，数组（新的在前），每条 `{id at old_sha new_sha source(job|router) job_id job_kind diff[] note}`；`diff[]` 每项 `{exit op(added|removed|changed) from to creds}`（`added` 只有 `to`，`removed` 只有 `from`，`changed` 在 server:port 变了时有 `from` / `to`、在类型或凭据变了时 `creds: true`，凭据本身不出）；`diff` 为空且 `note` 为空 = 配置变了但出口没变；`note` 非空 = 比不出差异的原因。
- `router exits`（算好的统计，不是原始点）：`{router{id,name} range step_s exits[{name tests fails success_pct fail_streaks delay_median_ms delay_max_ms conns current}] total{exits tests fails success_pct fail_streaks delay_median_ms delay_max_ms conns}}`。`tests` / `fails` 是这段时间测了几次延迟、几次没通（每 5 分钟一轮，没通的当场重测一次、重测通了算通，一轮算一次；三种范围都准）；`success_pct` 是通的比例（%，一位小数，没测过为 null）；`fail_streaks` 是「连着 ≥2 轮不通」出现了几段（同告警 `router_exits_down` 的条件）：1h 按每一轮数，6h / 24h 按 5 分钟一点数（一点一般一轮，有一次没通算没通），没测的点跳过不打断；7d / 30d 是小时汇总、看不出先后，为 null（要看用 `--range 24h`）。延迟只算通了的：1h 是每次的，6h / 24h 是每 5 分钟的平均，7d / 30d 是每小时的平均（最大值偏小）。`conns` 是最近一次采集的当前连接数；`current: false` 的出口已不在路由现在的配置里（`conns` 为 null）；范围内没有点、现在配置里有的出口也列出（`tests` 为 0）。
- `provider ls`：API 原样，每家 `{id name code panel_url timezone traffic_rule(min|max|sum|out|in) traffic_reset(month|billing|rolling30) remind_days}`，`timezone` 为 null = 跟随组织时区。`plan ls`：API 原样（按 `--provider` 筛、默认去掉已归档的），每个 `{id provider_id name cpu_cores mem_mb disk_gb bandwidth_mbps traffic_gb price_cents currency cycle notes archived_at machine_count}`，`price_cents` 是分（29999 = 299.99），`traffic_gb` null / 0 = 不限，`archived_at` 非 null = 已归档，`machine_count` 是在用（未退役）的机器数。`provider add / set`、`plan add / set` 输出改完后的那一项（同 ls 的一项；没有变化时不提交，输出现在的），`rm` 输出 `{id}`。

完整接口见仓库 `docs/API.md`，运维流程与何时才需要直接 ssh 见 `docs/OPS.md`。
