# 重构方案（2026-10）

- 依据：`docs/audit/2026-10-baseline.md`（下称「基线」）、PR #2/#3 的评审、`pm-backlog.md`（PM 走查，P-01–P-28），代码以 `origin/main` f1aa1eb0 为准。
- 原则：
  - 只做收益明确的重构，能用数据验收的优先；
  - 每个 PR 只做一件事，可以单独测试、单独 revert，迁移要可重复执行；
  - 纯搬家的 PR 不顺手改逻辑；
  - 不引入新框架、trait 层或 ORM。

## 各项明细

### R1 agent 上报事务拆分（基线 P2-5、P2-6、P2-7；backlog P-13）

- **收益**：这是生产 >1s 写最可能的来源。整点时，上报事务排在分区 DDL 和 `rollup_dirty` 热行后面，持锁时间被拉长。拆分以后每份上报的持锁时间预期下降一个量级。
- **风险**：
  - 去重语义依赖 `agent_state.last_seq` 和 `for update` 的原子性（`agent_api.rs:520-534`），改坏会导致重复入库或者丢报。
  - 改 info 写法会影响依赖 `info.caps/xray` 的地方（`reverse::unsupported`、`jobs::steps::wait_report`）。
- **依赖**：先做 PERF-0 观测（生产开 `pg_stat_statements` / `log_lock_waits`）拿到基线数字，否则无法验收。这是运维配置，不在本仓库改。
- **拆成 4 个 PR**：
  - **R1a 脏标记移出热路径**：`rollup_dirty`/`access_dirty` 的 upsert（`agent_api.rs:663-679`）改为在 `tx.commit()` 之后、用独立语句执行，并且只在 `touched_at` 落后 30 秒以上时才更新。
    - 验收：现有集成测试全部通过；新增测试「迟到样本仍会触发补算」；压测 50 个并发 agent 跨整点上报，没有锁等待日志。
  - **R1b info 只在变化时写**：拆出 `agent_heartbeat(machine_id, last_seq, last_report_at)` 新表（新迁移，回填一次），`agent_state.info` 的合并加上 `where info is distinct from ...`。
    - 验收：重复上报相同 info 时 `n_tup_upd` 不增加；`clock_skew_ms`、`caps` 的现有测试通过。
    - 回滚：revert 代码即可，新表留着无害。
  - **R1c 去重锁收窄**：`for update` 改为 `update agent_heartbeat set last_seq=$2 ... where last_seq < $2 returning`，用乐观方式判断是否重复。
    - 验收：保留并扩充「同 seq 重发只确认不入库」「中控重启后去重」的测试。
  - **R1d placement 原始化**：上报只写 rtt 原始样本，p50 移到 5 分钟一次的 rollup（`placement.rs:73-85`）里算。
    - 验收：矩阵接口输出和改之前在同一份数据上一致（快照测试）；上报事务里不再有数组拼接。
- **整体验收（P-13 原文）**：>1s 写的次数每小时下降 ≥80%，用 PERF-0 的前后数据对比。

### R2 汇总只写有变化的行，ping 改用脏标记（基线 P2-8）

- **收益**：每 5 分钟和每小时的全量覆盖写不再产生死元组，autovacuum 压力下降。
- **风险**：低。`is distinct from` 只是减少写入，结果不会变。
- **依赖**：没有。可以和 R1 并行，但为了前后数据能比，建议排在 R1a 之后。
- **PR 拆分**：
  - **R2a**：`db.rs:361-402` 的 4 条 upsert 加上 `where (...) is distinct from (excluded...)`。
    - 验收：汇总测试全部通过；连跑两轮，第二轮 rows_affected 为 0。
  - **R2b**：`ping.rs:303-318` 的 72 小时全量重算改为复用 `db::rollup_dirty`（需要新增 `ping_dirty` 表）。
    - 验收：agent 断线 8 小时后补传，对应小时会被补算（新测试）；每小时那一轮写入的行数下降。

### R3 保留期清理合并 + 分批删（基线 P2-9、复用项①）

- **现状**：保留期删除散在 `db.rs:404-436`、`access.rs:175-179`、`ping.rs:321-323`、`routers/collect.rs:1354-1356` 四处，每处都是一次性整批 delete。
- **做法**：
  - 新建 `retention.rs`，放一张「表、时间列、天数来源」清单，加一个 `delete_batched(table, col, cutoff, 5000)` 函数；四处改为调用它。
  - `routers/collect.rs` 只把 `rollup/cleanup`（`:1307-1360`）搬过来，采集逻辑不动。
- **收益**：分批删修复只需改一处；保留期策略能在一处看全。
- **风险**：天数来源有配置（`[retention]`）和面板设置（`settings.rs`）两种，要原样保留，不要统一成一种。
- **验收**：
  - 每张表的保留期测试都通过；
  - 新增测试「超过 5000 行时分多批删完」；
  - 日志里每张表仍然打印删除条数。

### R4 `settings::put_locked`（复用项③）

- **做法**：把 `ping.rs:201-209` 和 `probe_points/mod.rs:276-293` 里的「advisory lock + upsert app_setting」抽成一个函数。只有这两个调用方，抽一个函数就够了，不做通用设置框架。
- **验收**：两处原有测试都通过，diff 净减行数。

### R5 `views.rs`（1985 行）拆分

- **现状**：同一个文件里有简报（`brief`）、流量周期（`period_start/next_reset`）、实时视图缓存（`live*`）、流量（`traffic`）、加载（`load`）、总览（`overview*`）。
- **做法**：改成 `views/` 目录，下分 `mod.rs`（`MachineView` 和 `load`）、`live.rs`（缓存）、`traffic.rs`、`overview.rs`、`brief.rs`。对外路径用 `pub use` 保持不变，调用方不用改。
- **收益**：P-12（列表加模式、调优列）和 P-26（总览计数统一）都要改这里，拆开以后两个功能 PR 的冲突面变小，评审也更容易。
- **风险**：纯搬家，风险在合并冲突，不在逻辑。
- **验收**：`git diff --stat` 只有移动；`cargo test` 全部通过；`cargo build` 没有新警告；不改任何 SQL。

### R6 `api/machines.rs`（1794 行）拆分

- **做法**：按文件里已有的分节拆成 `machines/{mod,patch,series,retire,agent_ops,billing}.rs`，`patch_tx/patch_nobump/patch_write` 留在 `patch.rs`。
- **依赖**：等 PR #2（它改了 `patch_write`）合并后再做；P-19（替换前置检查统一）会改 retire 和 replace 附近的代码，所以要等 P-19 合并后再做，或者紧接在它之前做（见下文「冲突与顺序」）。
- **验收**：同 R5。

### R7 `jobs/steps.rs`（1425 行）拆分

- **做法**：文件已经按「上架 `:196` / 退役 `:1072` / 补偿 `:1274`」分好节，照着拆成 `steps/{provision,retire,compensate}.rs`。`steps/replace.rs` 已经是这种组织方式，这次是和它对齐。
- **依赖**：P-18（作业超时）主要改 `jobs/mod.rs`，冲突小，可以并行。
- **验收**：同 R5。

### R8 `jobs/mod.rs`（1340 行）：不做

这个文件是作业引擎本身（定义、领取、租约、推进、清理），内聚度高，几个函数之间强相关。拆开只会让调用链变得更难跟，看不到收益。P-18 在它里面加超时是局部改动，不需要先重构。

### R9 `routers/collect.rs`（1731 行）：其余部分不做

采集脚本拼装、快照构建、采集循环是一条完整的管道，拆开要把很多私有类型提升成 pub，收益小。只有汇总和保留期那一段（`:1307` 以后）合并进 R3。P-22（统计口径统一）只改 `summary` 和列表查询，直接改就行。

### R10 `fleetctl/src/cmds.rs`、`ops.rs`：不做

这两个是 CLI 的子命令表，长但平铺，每个子命令都很独立，没有冲突热点。拆开对使用者和维护者都没有实际收益。

### R11 命名：不单独做

缩写（`es/ps/ac/mu/mt/du/dt`）集中在 `agent_api.rs` 和汇总相关代码里，R1 和 R2 会改到这些函数，到时候在 diff 范围内顺手改成全名。不单独开一个改名 PR，免得制造无意义的冲突。

### R12 只读运维能力从 exec 拆出 `logs` scope（安全；基线 P1-1）

- **收益**：只看日志或诊断的密钥不必再拿 exec（也就是对全机群的 root 执行权）。
- **依赖**：P-09（诊断页签）和 P-21（exec 审计脱敏）也会改 `api/exec.rs`、`auth.rs`，三件事放在同一个迭代里按顺序做：先 R12（scope），再 P-21，最后 P-09，避免互相改同一段代码。
- **PR 内容**：
  - `auth.rs:129` 把 `machines/*/logs`、`server/logs` 改为需要 `logs` 或 `exec` 中的任意一个；
  - 密钥创建界面增加 logs scope。
- **验收**：
  - 只有 logs scope 的密钥能看日志，调用 `/exec` 返回 403；
  - exec 密钥的行为不变（兼容）。

## 推荐顺序（每一步都是一个独立 PR，可单独 revert）

1. PERF-0 观测（运维配置，不进仓库）→ 拿到基线数字
2. R1a → R1b → R1c → R1d（P-13）
3. R2a、R4（可以并行）
4. R5（views 搬家）→ 然后 P-12、P-26、P-17/P-06 并行开发
5. R3、R2b
6. R12 → P-21 → P-09
7. 等 PR #2、P-19 合并后：R6、R7

不在计划内：R8、R9 的其余部分、R10、单独的改名 PR。重新评估的条件：某个文件连续两个迭代成为冲突热点，或者新功能必须在它内部再抽一层。
